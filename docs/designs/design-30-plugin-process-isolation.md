# Design 30: plugin process isolation, a uid boundary between the server and the code it runs

Status: proposed 2026-10-16 for the operator's decision, revised 2026-10-16 after an architecture review and a security review the same day (their findings are folded into Options, Decision, The change, Verification and Risks). Closes `PROGRAM.md` KI-22. No code is written. This is a read-only design produced from the `integration` checkouts below; the facts in "What a plugin child can reach today" were verified in source before anything else was decided. Slices S1 to S3 below; none built.
Date: 2026-10-16.
Reference: lattice-server `integration` at 3231a08 (production is `alpha-0.2.2a125`, the a126 switch staged), lattice-sdk `integration` at 042370c, lattice-plugin-vpn-core at 9e7b61f (0.11.0-alpha.7), lattice-plugin-sub-store at f868982 (0.17.0-alpha.2), lattice-plugin-netguard at 1b37d1b (0.2.0-alpha.6), lattice-plugin-wireguard at bc45ce7 (0.2.0-alpha.6), umbrella at 223cedf, production compose `.claude/ops/compose-a126.yml`.

## Summary

lattice-server runs system plugins as its own operating-system identity. The runner calls `exec.Command` on the staged artifact with `SysProcAttr{Setpgid: true}` and nothing else (`lattice-server/internal/plugin/system_runner.go:1169` for a one-shot v1 invocation, `system_transport.go:418` for a pooled stdio-json-v2 worker). The child inherits the server's uid (`lattice`, the account the container's entrypoint drops to), its mount namespace, its network namespace, and its supplementary groups, one of which is `65532`, the probe's group. A compromised or malicious signed plugin is therefore the server as far as the operating system is concerned: it can read `master.key` and the whole state tree, open the lattice-probe socket directly and skip the `vpn:probe` scope check, the per-operator limits and the audit, and reach the server's own loopback API. The signature chain proves who built the artifact; it does not confine what the artifact does once it runs.

This design puts an operating-system boundary under the signature: each plugin child runs as a per-plugin unprivileged uid that owns none of the server's files, carries none of its supplementary groups, and holds no capabilities. The host-call path (a plugin's only legitimate way to reach the fleet) is a set of inherited pipes and survives the uid change untouched, so the four production plugins keep working with no change to their code. The boundary is enforced by the kernel's own discretionary access control and by stripping capabilities at `execve`, needs no new Go dependency, and keeps the server pure Go. After it ships, a plugin can no longer reach `master.key`, the state files, the audit WAL or the probe socket, and can no longer signal or trace the server or a sibling plugin. It does not fix everything: the child still shares the server's network and PID namespaces, so it keeps full network egress and a view of process metadata, and the server's loopback API stays reachable though it serves no sensitive data without a credential. Those residuals are named and scoped to a later slice.

## What the operator asked

KI-22, recorded 2026-10-09 after a122, and the closing note in design 27's security section: plugin processes run as the server's uid with its mount namespace and group `65532`, so a plugin can open `/run/lattice-probe/probe.sock` directly and bypass the probe's server-side gate. The KI says this "adds no reach" because the plugin already reads everything that uid reads and the probe's own address policy and in-flight ceiling still apply, and asks for the fix to be "plugin process isolation (own uid or a mount namespace without the socket directory)." This design is that fix, and it widens the frame the KI drew: the probe socket is one of several things the shared uid exposes, and the isolation that closes the socket closes most of the rest at the same time.

## What a plugin child can reach today

Read from the checkouts above and the production compose on 2026-10-16; both reviews confirmed each item against source.

1. **How the child is started.** `runInvocation` (v1, `system_runner.go:1166`) and `startSystemWorkerObserved` (v2, `system_transport.go:415`) both build `exec.Command(path)`, set `cmd.Dir` to the plugin's `0700` working directory under `LATTICE_PLUGIN_RUNTIME_DIR`, set `cmd.Env` from `childEnv()`, set `cmd.SysProcAttr = &syscall.SysProcAttr{Setpgid: true}`, and pass one extra file descriptor (fd 3, the host-response pipe) plus stdin, stdout and stderr. `Setpgid` is the only attribute. There is no `Credential`, no `Unshareflags`, no `Chroot`, no `Pdeathsig`.
2. **What uid it runs as.** The image's `docker-entrypoint.sh` runs the server through `su-exec lattice`, so the server process is uid `lattice` (uid 100 in the alpine image) with an empty capability set and the supplementary group `lattice-probe` (gid 65532). A root-to-nonroot `setuid` clears capabilities, so the server holds none today; a forked child inherits the uid, the groups and the empty cap set. The compose file gives the `lattice-server` container no `user:`, no `cap_drop`, and no `security_opt`, so the container starts as root with Docker's default capability and seccomp profile and the entrypoint does the drop.
3. **The environment it gets.** `childEnv()` (`system_runner.go:1806`) forwards only the variables named in `EnvAllowlist` and always adds a fixed `PATH`. In production `EnvAllowlist` is empty (`server.go:844`, confirmed by the comment and by `LATTICE_PLUGIN_RUNTIME_ENV` being unset in the compose file), so no host environment, no secret and no `LATTICE_*` setting leaks into the child. This part is already tight.
4. **The probe socket.** `/run/lattice-probe/probe.sock` is mode `0660` owned `65532:65532` on a tmpfs the compose file creates mode `0770` owned `65532:65532`. The server reaches it because uid `lattice` carries supplementary group `65532`. A plugin child carries the same group, so a direct `net.Dial("unix", ...)` from the child succeeds and the request never passes through `vpncore_probe.go`, where `probeScope = "vpn:probe"`, `probeMaxRunsInFlight`, `probeMaxRunsPerHour` and the `vpncore.probe` audit record live. The probe's own SSRF policy and its 32-run engine ceiling still apply, so this is not arbitrary outbound; it is unaudited, unmetered, unauthorized probing.
5. **The state tree.** `/var/lib/lattice` is the `./data` bind mount, owned `lattice:lattice`. Every sensitive file in it is mode `0600` owned by `lattice`: `master.key` (the at-rest key that decrypts every stored credential, `secret.go:281`), `state.json` and `state-hot.db` (`store.go`, `bolt_state.go`), the audit WAL (`audit/wal.go:162`), `logs.db`, `metrics.db` and `trace.db`, and the plugin bundle cache and runtime dirs (`0700`). Because the child is uid `lattice`, discretionary access control grants it read and write on all of them, and the directory names and sizes are visible for traversal. Reading `master.key` plus `state-hot.db`/`state.json` is full credential disclosure. Writing the audit WAL is tampering, bounded only by the hash chain and the off-box anchoring that make the tamper detectable after the fact, not prevented.
6. **The plugin tree.** `/plugins` is mounted read-only, so a child cannot swap a bundle or edit `.trust.json`, but it can read every other plugin's artifact and the trust policy.
7. **The network namespace.** The child shares the server's netns, so it has the server's full network reach, not loopback alone: outbound egress to anywhere the container can reach (exfiltration of anything it holds, the docker bridge gateway, host-published ports, any cloud metadata address), and the server's own API on `127.0.0.1:8088`. The child holds no admin cookie or token, so it cannot drive authenticated endpoints, but it can hit any unauthenticated surface, and because the server's default trusted-proxy set includes loopback and the private ranges (`client_ip.go`), a child that reaches the API over loopback or the bridge may be able to set `X-Forwarded-For` and spoof the client address that per-IP limiters and audit attribution key on, if `TrustProxy` is on. The probe is on its own `probe` bridge network that the server container is not joined to, so the socket, not the network, is the probe's only exposure today. Abstract unix sockets, if any exist in the netns, have no filesystem and no DAC and would stay reachable; none is expected, and S2 verifies it.
8. **The PID namespace.** The child shares the server's PID namespace and runs as the same uid, so it can `kill` the server or any sibling plugin, and read another process's `/proc/<pid>/mem`, `fd` and `environ`. `Setpgid` only isolates signal delivery for teardown; it is not a privilege boundary.
9. **No docker socket.** The compose file mounts no `/var/run/docker.sock` into the server container (volumes are `./data`, `./plugins:ro` and the `probe-run` tmpfs only). There is no container-escape-to-host path through a mounted daemon socket, which removes the worst case from the table.

The precise exposure, then: a plugin that stops speaking the protocol and instead uses the Go runtime it already is can read the master key and all state, forge or probe the fleet through the probe socket without a trace in the audit log, signal or trace the control plane, and egress freely. The signature says the artifact is the one the operator approved; nothing stops that artifact from doing any of this.

## Options

Four mechanisms can put a boundary between the server and its plugin children. Costs are specific to this codebase (`os/exec` with `SysProcAttr`, pure Go, zero CGo, an ADR for any new dependency) and this compose (non-root entrypoint via `su-exec`, Docker default caps and seccomp, no `no-new-privileges` on the server container).

| Option | Mechanism | What it closes | Cost | Verdict |
|---|---|---|---|---|
| (a) per-plugin uid | `SysProcAttr.Credential` drops each child to its own uid, in no shared group, owning none of the state, holding no capabilities | probe socket, `master.key` and all state and the WAL (DAC), cross-uid `kill`, `ptrace` of the server and of siblings | file capabilities on the server binary; a relaxed artifact-mode invariant; a uid-per-plugin mapping | chosen |
| (b) mount namespace or chroot | `Unshareflags: CLONE_NEWNS` or `SysProcAttr.Chroot` to a tree without the socket or the state | probe socket and state by making them absent from the child's view | `unshare(CLONE_NEWNS)` needs `CAP_SYS_ADMIN`; `chroot` needs `CAP_SYS_CHROOT`; a user namespace to avoid `CAP_SYS_ADMIN` is blocked by Docker's default seccomp | rejected as the primary, kept as defense in depth |
| (c) move the socket, authenticate the channel | socket leaves the server container's view; server reaches the probe over TCP with a per-boot token held only in server memory | probe socket only | server joins the `probe` network; probe gains a token check; a new TCP listener | rejected as insufficient alone; folded in as probe hardening |
| (d) Landlock or seccomp in the child | the child self-restricts filesystem, socket and network access before real work | whatever the filter names, if the child applies it | a sandboxing library or raw syscalls; binds only plugins that choose to apply it | rejected as a boundary; usable as SDK-side defense in depth |

### (a) a per-plugin uid, enforced by the host

The server forks each plugin child with `SysProcAttr.Credential` set to that plugin's own uid and gid (from a reserved range, see "The change"), with the supplementary group list cleared. The standard library then issues `setgroups`, `setgid` and `setuid` between fork and exec (`syscall/exec_linux.go`), so the child drops to its uid, out of group `65532`, with no shared supplementary group. Discretionary access control now denies it the probe socket (`0660 65532:65532`, no world bits and no group match), `master.key`, every `0600 lattice` file and the WAL, and the cross-uid relationship denies it `kill` and `ptrace` of the server and of any sibling plugin on its own uid. The host-call pipes (stdin, stdout, stderr, fd 3) are inherited open descriptors and survive `setuid` and `execve`, so the plugin protocol is unaffected and no plugin code changes.

The cost is real and specific, and the first revision of this design got it wrong in three ways that the two reviews caught; the corrected mechanism is below.

- **Capabilities must come from the binary, not from the ambient set.** A process can only `setuid` to an unrelated uid if it holds `CAP_SETUID` (and `CAP_SETGID` to set the group, and `CAP_KILL` to later reap the cross-uid child), so the `lattice` process must hold these three. They must not be granted as ambient capabilities: the ambient set is the one set that survives `execve` into an unprivileged program, and because the server runs as a non-zero uid, the child's `setuid` to its plugin uid does not clear it, so an ambient grant would re-appear in the plugin's permitted and effective sets after `execve` and let it `setuid(100)` straight back to `lattice`. The grant is therefore file capabilities on the server binary (`setcap cap_setuid,cap_setgid,cap_kill+ep /usr/local/bin/lattice-server` in the image). File capabilities land in the server's permitted and effective sets on its own `execve` but are not in its inheritable set, so a plugin child's `execve` into an artifact with no file capabilities computes an empty permitted set and the plugin holds nothing. This keeps `su-exec lattice` in the entrypoint unchanged: file capabilities apply on the server's `execve` whoever execs it, as long as `no-new-privileges` stays off, which this design requires anyway.
- **No chown; relax the artifact-mode invariant instead.** A `chown` of the staged artifact to the plugin uid is impossible without `CAP_CHOWN`, and it would also lock the server out of re-verifying the artifact's SHA and of `os.RemoveAll` on the generation directory at cleanup and retirement (`system_runner.go:327`, `:553`), both of which run as `lattice`. The artifact and its generation directory stay owned by `lattice`; the directory is made traversable and the artifact executable by "other" (generation directory `0711`, artifact `0555`, both still `lattice`-owned and not group- or world-writable, so a plugin cannot create or replace a file in the directory). The dropped child, matching "other", can `chdir` in and `exec` the artifact and nothing else. This requires relaxing the exact `info.Mode().Perm() != 0o700` assertion in `stagedArtifactMatches`/`checkStagedArtifact` (`system_runner.go:804`, `:1906`) and the `0o700` directory check (`:799`) to the new modes, while keeping the artifact owned by `lattice` (the anti-swap property, on top of the SHA pin that already defends it). That invariant is security-sensitive and its change carries its own review in S1.
- **Per-plugin uids, not one shared uid.** A single shared plugin uid leaves every plugin able to `kill`, `ptrace` and read the memory and fd-3 host-call pipe of every other plugin, which would defeat the per-plugin capability-scope model exactly where axiom 3 is supposed to enforce it. `setuid` to a bare numeric uid needs no `/etc/passwd` entry, so the runner assigns a uid per plugin from a reserved range at no extra cost and with no image accounts, and the `lattice`-owned permission scheme above is uid-agnostic, so per-plugin uids cost nothing beyond the mapping.

What (a) does not fix: the child still shares the server's network namespace, so it keeps full egress and the loopback API stays reachable (serving no sensitive data without a credential, and with the `X-Forwarded-For` caveat of item 7); and it shares the PID namespace, so process metadata under `/proc` is still visible, though signalling and tracing across uids are gone. These are the residuals, scoped to S3.

### (b) mount namespace or chroot

Making the socket and the state simply absent from the child's filesystem view is conceptually the cleanest confinement, and the KI names it. In this container it is the expensive one. `unshare(CLONE_NEWNS)` requires `CAP_SYS_ADMIN` in the current user namespace, a broad capability the server does not want; `chroot` requires `CAP_SYS_CHROOT` and a chroot tree to populate with the artifact and its `PATH` binaries. Avoiding `CAP_SYS_ADMIN` by unsharing a user namespace first is blocked by Docker's default seccomp profile, which denies `unshare` and `clone` with `CLONE_NEWUSER` to a process without `CAP_SYS_ADMIN` (verified against moby's current `profiles/seccomp/default.json`: the `unshare` group and the `CLONE_NEWUSER` `clone` paths are gated on `CAP_SYS_ADMIN`). So (b) needs either a broad capability or a custom seccomp profile layered onto the container, against a doctrine of fail-closed minimalism. It is kept as a defense-in-depth layer that composes with (a) later, not as the first boundary.

### (c) move the socket out, authenticate the channel

This closes exactly the one hole the KI's title names and nothing else. The probe socket moves to a volume the server container does not mount; the server joins the `probe` network and calls the probe over TCP with a bearer token minted once per boot and held only in server memory, which the probe checks. A plugin child, sharing the netns, could reach the port but cannot produce the token, which lives in the server's address space and is itself protected by the uid boundary of (a): without (a) the token is readable from the server's memory through `/proc`. It leaves `master.key`, the state tree, the audit WAL and the loopback API exactly as exposed as today, so as the answer to KI-22 it is a partial fix wearing the KI's own words. It is worth doing as probe-side hardening and depends on (a), not the reverse; it is folded into S3.

### (d) Landlock or seccomp applied in the child

Landlock could, in principle, deny the child the state directory and (from ABI 9, `LANDLOCK_ACCESS_FS_RESOLVE_UNIX`) connecting to the probe socket by path; ABI 4 could deny the loopback TCP connect. But ABI 9 is a 2026 patch series not present in the production kernel, Go has no standard-library Landlock and would need a vetted dependency, and most fundamentally the host cannot run arbitrary code between fork and exec through `os/exec`, so the restriction would have to be applied by the plugin itself as its first action in the SDK runtime, which a malicious plugin would not do. That makes (d) a hardening the honest SDK can adopt, never a boundary the host enforces. It is noted for the SDK, not chosen.

## Decision

Take (a): plugin children run as a per-plugin unprivileged uid, enforced by the host with the kernel's access control and an empty capability set at `execve`, the three enabling capabilities carried as file capabilities on the server binary, and the staged artifact left `lattice`-owned with a relaxed mode rather than chowned. Fold (c) into the probe as a token on the probe channel in S3, so that even a future change that re-exposes the socket does not re-open the bypass. Keep (b) and (d) as named defense-in-depth layers for later, not as the gate.

The reasons, against the alternatives and confirmed by both reviews: (a) is the only option that is host-enforced (not plugin-cooperative), pure Go with no new Go dependency (`SysProcAttr.Credential` is standard library), fail-closed (a child that cannot drop does not start), and closes the largest share of the exposure in one change (probe socket, master key, all state, the WAL, cross-uid signalling and tracing) rather than the socket alone. (b) buys little more than (a) for a broad capability or a custom seccomp profile. (c) alone leaves the credential store exposed. (d) is not a boundary. (a) fits axiom 3 directly: "capability gates confine what may even be asked" of the system, now extended from the node and the broker down to the operating-system identity of the code the control plane runs, and it strengthens the Platform pillar's promise of "brokered capabilities" with an isolation the broker could not previously assume.

The capability trade is stated plainly for the operator. The server binary gains `CAP_SETUID`, `CAP_SETGID` and `CAP_KILL`, which it holds in effect for its whole life and uses only to downgrade and later reap its children. A remote-code-execution bug in the server could use `CAP_SETUID` to become container root, which it could not do today. This is a net gain only because S2 pairs the grant with `cap_drop: [ALL]` and an explicit `cap_add` of exactly those caps, so that container root has a three-capability bounding set instead of Docker's default dozen-plus; the entrypoint's one-time `chown -R` at boot is guarded to run only when the data directory is not already owned by `lattice`, so no `CAP_CHOWN` is added and the bounding set stays at three. Granting the server the means to confine the code it runs, inside a minimal bounding set, is the trade, and it is the operator's to accept.

What the decision explicitly does not fix, restated so it is not mistaken for complete: the shared network namespace (full egress remains; the loopback API stays reachable but serves nothing sensitive without a credential, a protection that holds only as long as no unauthenticated internal endpoint is added, and with the `X-Forwarded-For` caveat) and the shared PID namespace (`/proc` metadata of other processes is still visible, though signalling and tracing across uids are gone). Narrowing these is S3.

## The change

### Runner (`lattice-server/internal/plugin`)

Add a plugin-uid resolver to `SystemRunnerOptions`: a reserved base uid and a deterministic, collision-free map from plugin id to a uid in a reserved range (the production set is four plugins and the pool cap is 32, so a small base-plus-index assignment held in the runner is enough; the gid matches the uid and no `/etc/passwd` entry is needed). When the option is set, `runInvocation` (v1) and `startSystemWorkerObserved` (v2) set `cmd.SysProcAttr.Credential = &syscall.Credential{Uid: u, Gid: u, Groups: []uint32{}}` alongside the existing `Setpgid`; the empty `Groups` with `NoSetGroups` left false makes the runtime call `setgroups(0, ...)` and clear the inherited supplementary groups, dropping `65532`. When the option is unset, behaviour is exactly as today. Relax the staged-artifact checks: the generation directory is created and kept at `0711` and the artifact at `0555`, both `lattice`-owned, and the `0o700` assertions at `system_runner.go:799`, `:804` and `:1906` are updated to the new modes with an added assertion that the artifact's owner is the server's uid (the anti-swap property, alongside the existing SHA pin). Do not chown anything. Cross-uid teardown (`terminateProcessGroup`, `system_runner.go:1424`/`:1530`, `system_transport.go:524`) relies on `CAP_KILL`, now held by the server; add a teardown test that runs under the drop. The host-response pipe, stdin, stdout and stderr are already passed as inherited descriptors and need no change.

### SDK (`lattice-sdk`)

No change required for the boundary. The host-call client reads fd 3 from `LATTICE_HOST_RESPONSE_FD` (`plugin/host.go:204`) and that descriptor is inherited across the drop. The SDK is the natural home for the optional (d) self-sandbox later, behind a runtime flag, but that is not part of closing KI-22.

### Image (`lattice-server/Dockerfile`, `docker-entrypoint.sh`)

Add `setcap cap_setuid,cap_setgid,cap_kill+ep /usr/local/bin/lattice-server` in the final stage, which pulls in libcap's `setcap` as a build-time image package (noted below as a trusted-computing-base addition). Keep `su-exec lattice` in the entrypoint unchanged; file capabilities apply on the server's own `execve` regardless of who execs it, and the server then holds the three caps in permitted and effective but not inheritable, so plugin children inherit none. Guard the entrypoint's `chown -R lattice:lattice` so it runs only when the data directory is not already owned by uid 100, so that `cap_drop: [ALL]` in S2 does not need `CAP_CHOWN`. No new per-plugin accounts are created; the runner assigns bare numeric uids.

### Compose (`.claude/ops/compose-aNNN.yml`)

Set `LATTICE_PLUGIN_UID_BASE` (and the range) on the `lattice-server` service to turn the drop on in S2. In the same slice add `cap_drop: ["ALL"]` with `cap_add: ["SETUID","SETGID","KILL"]`, so the server's bounding set is exactly the three caps the boundary needs and a server RCE that becomes root is held inside them. Do not set `no-new-privileges` on the server container: it would make `execve` ignore the file capabilities, so the server would start with no caps, the child drop would fail, and no plugin would run (fail-closed, caught in precheck). The probe service is unchanged by (a); (c) adds the probe-channel token in a separate probe release in S3.

### Plugins

None. Verified: the four production plugins do no direct filesystem, network or process I/O from their runtime binaries (`path/filepath` appears only for in-memory path handling; sub-store's `net`, `os/exec` and `syscall` imports are confined to its `tools/` and `_test.go` files, not the plugin entrypoint), and reach the host only through the SDK's inherited pipes. The per-plugin uid takes away nothing they use.

## Migration and rollback

Ship in order. S1 ships the server image with the runner option and the `setcap` line, with `LATTICE_PLUGIN_UID_BASE` unset, so plugin children still run as `lattice` exactly as today; the observable spawn behaviour is identical with the drop off, though the server process does now hold the three file capabilities from S1 on, which is a latent posture change rather than a no-op, and the drop itself is first exercised and proven in S2, not S1. Keep the S1 window short for that reason. S2 is the compose switch that sets the uid base and adds `cap_drop`/`cap_add`, which is the step that turns the boundary on and the step that closes KI-22. Rollback at any point is the standard image or compose rollback already in `switch-aNNN.sh`: unsetting the env returns to shared-uid children on the same image, and rolling the image back removes the `setcap` and the entrypoint guard. The probe-channel token (c) ships as its own probe release and compose change in S3, independent of (a), and rolls back the same way.

## Verification

### Tests

These run inside the built image as the real `lattice` user with the shipped file capabilities, not as root and not as the developer user, because the privilege situation is the whole point and a test run as root proves nothing about it.

- A child started with the credential set reports its per-plugin uid, not the server's, in `/proc/self/status`.
- The child's `/proc/self/status` `Groups` line does not contain `65532` (this is the assertion that proves the supplementary groups were cleared; the socket-dial test alone would miss a `NoSetGroups` regression).
- The child's `CapEff`, `CapPrm`, `CapInh` and `CapAmb` are all zero, and an attempted `setuid(0)` and `setuid(100)` from the child fails with EPERM (this is the assertion that proves the capability climb is closed; a negative control with a deliberately wrong cap setup must make this test fail).
- The child cannot open a stand-in socket owned by a foreign gid at `0660`, and cannot read a `0600` file owned by the server uid (stand-ins for the probe socket and `master.key`); the same two attempts with the credential unset succeed, so the test proves the boundary and not a missing file.
- The child can `chdir` into its `0711` generation directory and `exec` its `0555` artifact, and the relaxed mode checks pass.
- A host call completes after the drop (fd 3 round-trip), so the protocol is proven unbroken.
- The server reaps a timed-out or cancelled child group across the uid boundary (proves `CAP_KILL` is held and used).
- If per-plugin uids are adopted as specified, a child cannot `kill` or `ptrace` a sibling plugin on a different uid.

### Production precheck

Add a precheck step to `.claude/ops/precheck.sh`. The candidate boots there with `--network none` against a copy of production data, so the step asserts what that environment can show: the four plugins load with `0 rejected` (already checked); a diagnostic plugin run through the same `exec` path as a real plugin reports its uid, its empty `Cap*` and `Groups` without `65532`, and failed opens of `/run/lattice-probe/probe.sock` and `/var/lib/lattice/master.key`; and the server process's own `CapEff` matches the three expected caps. The broker probe-call leg cannot run under `--network none` and is not asserted there; it is covered by the live-switch check below. The diagnostic is a throwaway plugin or test binary, never a shipped server endpoint that forks a child, because that would add a privileged surface to the control plane.

### Live switch

`switch-aNNN.sh` already prints the server process `Uid`/`Groups` and the socket mode after the switch. For the switch that turns the drop on, add an assertion that reuses the S2 diagnostic: a plugin child reports its per-plugin uid, empty capabilities, no group `65532`, and a failed socket open, and that a probe call driven through vpn-core's broker path still returns. The precheck proves the boundary against a data copy; the live switch proves it on the real container before the switch is declared done.

## Verify on hkg before implementation (read-only)

Run these on the production host to confirm the facts the design rests on, changing nothing:

- `docker exec lattice-server id` and `docker exec lattice-server sh -c 'grep -E "Cap|Groups" /proc/1/status /proc/self/status'`: confirm the server runs as uid `lattice` with group 65532 and holds no capabilities today.
- `docker inspect lattice-server --format '{{.HostConfig.CapAdd}} {{.HostConfig.CapDrop}} {{.HostConfig.SecurityOpt}}'`: confirm no caps dropped, no `no-new-privileges`.
- `docker exec lattice-server sh -c 'ls -ld /var/lib/lattice /var/lib/lattice/plugin-runtime /run/lattice-probe; ls -ln /run/lattice-probe /var/lib/lattice'`: confirm the socket is `0660 65532:65532`, the state files are `0600 lattice`, and read the ancestor directory modes that the child must traverse.
- `docker exec lattice-server sh -c "grep '@' /proc/net/unix"`: confirm no abstract unix socket is open in the netns.
- `docker inspect lattice-server --format '{{json .Mounts}}'`: confirm no docker socket is mounted.
- `docker version --format '{{.Server.Version}}'`: the default inheritable-capability behaviour changed across recent Docker releases, which matters to the file-capability reasoning.
- `docker exec lattice-server sh -c 'cat /proc/sys/kernel/yama/ptrace_scope'`: the sibling-plugin `ptrace` residual depends on this.
- For option b's feasibility only, if it is ever revisited: `uname -r` and `cat /proc/sys/kernel/unprivileged_userns_clone` for unprivileged user namespaces, and `apk info -e libcap` in a candidate image build to confirm `setcap` is available.

## Slices

- **S1. The uid boundary, off by default.** Runner credential option with the per-plugin uid map, the relaxed artifact-mode checks with the owner assertion, the `setcap` line and the entrypoint `chown` guard, and the tests above run in the built image. Server release with the option off. This is the whole of KI-22's fix bar turning it on; the mode-invariant change carries its own review.
- **S2. Turn it on and prove it.** Compose switch setting the uid base, adding `cap_drop: [ALL]` with the three-cap add-list, the precheck step and the diagnostic child, and the live-switch assertion. This is the slice that closes KI-22.
- **S3 (optional). Narrow the residuals.** The probe-channel token (option c) as a probe release; and, if the shared network namespace is judged worth closing, either a separate network namespace for plugin children (cost: `CAP_NET_ADMIN` or a userns, the same seccomp consideration as option b) or binding the server's API where the plugin uid cannot reach it; and, as a hardening refinement, carrying the server caps as permitted-only and raising them to effective just around the spawn. Scoped but not scheduled.

## Risks

- **File capabilities depend on `no-new-privileges` staying off.** If a future hardening pass sets `no-new-privileges` on the server container, `execve` ignores the file capabilities, the server starts with none, and every plugin drop fails. That is fail-closed and caught in precheck, but it is a non-obvious coupling: this container must not get `no-new-privileges` while it relies on file-cap elevation. The compose comment and this design record it.
- **The capability trade is a real escalation that S2 must bound.** The server holding `CAP_SETUID` means a server RCE can become container root; it is a net gain only with `cap_drop: [ALL]` and the three-cap add-list in the same slice. Shipping the `setcap` (S1) before the `cap_drop` (S2) leaves a window in which the server holds the caps inside Docker's full default bounding set; keep that window short, which is another reason S1 ships with the drop off and S2 follows promptly.
- **The artifact-mode invariant is security-sensitive.** Relaxing the exact `0700` check to `0711`/`0555` while keeping the owner-is-`lattice` assertion and the SHA pin must be reviewed on its own; the directory staying `lattice`-owned and not group- or world-writable is what keeps a plugin from planting or swapping an artifact.
- **It is not total isolation.** The shared network namespace (full egress, loopback API, `X-Forwarded-For` caveat) and the shared PID namespace (`/proc` metadata) remain, named above and scoped to S3. Calling KI-22 closed after S2 means the credential store, the state files, the audit WAL and the probe socket are out of a plugin's reach and a plugin can no longer signal or trace the server or a sibling; it does not mean a plugin is fully sandboxed. `PROGRAM.md` should say exactly that.
- **Per-plugin `ptrace` depends on the host's `yama.ptrace_scope`.** The cross-uid barrier blocks `ptrace` of a different uid regardless, but confirm the production value rather than assuming it.

## Dependency note

The boundary adds libcap (`setcap`) to the server image as a build-time package and makes it part of the trusted computing base for the isolation. `SysProcAttr.Credential` itself is Go standard library and adds no module dependency. The hard-constraint ADR rule is written for Go module dependencies, so a strict reading does not trigger it, but because this package is load-bearing for a security boundary it is recorded here and should carry a one-line ADR, consistent with the doctrine's "every new dependency justified."

## Decisions for the operator

One choice here is the operator's rather than the agent's: whether to accept the server binary holding `CAP_SETUID`, `CAP_SETGID` and `CAP_KILL` for the purpose of downgrading and reaping its children, bounded by `cap_drop: [ALL]` so that a server compromise that climbs to root is held inside those three capabilities. That is the price of a host-enforced boundary short of a user namespace. Everything else (the reserved uid range and mapping, the relaxed mode scheme, the test and precheck shape) an agent may decide and build. Switching the live image or plugin set to the version that turns this on is a production switch and rides the standard precheck, backup, health and rollback gates already granted for the open backlog.
