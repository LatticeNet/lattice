# Design 29: Monitoring paths, operator-defined checks between nodes with a week of history

Status: accepted 2026-10-16 after an architecture review and a security review the same day (their findings are folded into D1 to D6, D10, Slices and Risks); the operator asked for this work and granted release authority the same day (`PROGRAM.md` Decisions 2026-10-16). Slices M1 to M4 below; none built.
Date: 2026-10-16.
Reference: lattice-server `integration` at a6caff4 (alpha-0.2.2a124), lattice-dashboard `integration` at 2ce7dd2, lattice-node-agent `integration` at c8c3a8f, lattice-sdk `integration`, umbrella at 4608e85.

## Summary

Monitoring today answers one question well (is something down right now) and the rest poorly. Latency checks run from one node, `cd-hs-sh`, and can only dial a node's sing-box TCP line port, so a node without a TCP line cannot be a target and a NAT node, whose public port differs from its listen port, shows as unreachable when it is fine. Five of 33 targets read "failed" on production on 2026-10-16 for that reason. History exists in the hot store but the console shows at most a single-source matrix and a per-pair column chart with p50, p95 and loss; operator monitors have no history view and cannot be edited.

This design makes a **path** (one source probing one target with one method) the unit of monitoring, lets the operator define the sources, the targets and the method, keeps a week of five-minute history by default (settable from 3 to 14 days), and shows fluctuation: median, spread, jitter and loss on one time axis, with gaps drawn as unknown. Every node can carry a **beacon**, a small authenticated UDP responder inside the agent that answers only probes signed for it by the server's keys, at a port and public address the operator sets per node. Because the beacon is the first thing an agent ever listens on, the doctrine sentence "nodes run an outbound-only agent" is amended in this design, and the beacon is off until an approved plan turns it on for a node.

## What the operator asked (2026-10-16)

The Monitoring pages work, but the presentation and the history of fluctuation are missing. The operator wants to define a set of probes: every agent has a port or path that can be probed, which may differ per node, possibly with authentication, convenient to reach but safe from attack; the operator can have agent A probe agent B and define the source and target combinations; at least the last three days of data are kept, extendable to seven; the framework that added the `cd-hs-sh` latency probes should be the basis. Optimise the Monitoring pages end to end: UI, UX, logic and the data framework.

## Facts this design rests on

Read from the `integration` checkouts on 2026-10-16; file and line references are in the survey recorded in the vault ledger of that date.

1. **Checks.** `model.Monitor` kinds are `tcp` and `http` (run on agents) and `tls` (run on the server). `icmp` is a constant the server refuses to create. POST always mints a new id; there is no edit route. Defaults 30 s interval, 5 s timeout. HTTP counts any status under 400 as up and carries no headers.
2. **Latency probes.** `LatencyProbeConfig` in `state.json` lists source node ids (default `cd-hs-sh`), an "overseas" auto-target rule, include and exclude lists and disabled pairs. A planner every 2 minutes turns it into one generated `tcp` monitor per target, shared by every source, dialing that target's sing-box TCP line port on its public IPv4 and never port 22, an sshd port or a knock-gated port. A node with no TCP line is "not probeable".
3. **Agent.** The agent never listens. Each cycle (10 s) it pulls `/api/agent/monitors`, runs one goroutine per monitor (TCP dial, HTTP GET), and posts batched results; the queue is in memory, 2000 results. It holds no `CAP_NET_RAW` when installed with a run user; a default install runs it as root without a capability bound. No node-side veto covers monitors.
4. **Storage.** With the hot store on (production), results live in `state-hot.db` (bbolt): raw rows capped at 1440 per pair, histogram rollups at 5 minutes for 48 hours and 1 hour for 8 days, one latest record and fail streak per pair. A result stamped more than 24 hours old is refused. metricsdb holds no monitor data.
5. **Already pair-shaped.** Rows, rollups and the latest record are keyed by (monitor, source node). What is missing is first-class configuration of pairs, per-pair targets and a history API for anything but generated latency monitors.
6. **Console.** `MonitoringView.vue` has four layers (Incidents, Topology, Monitors, Latency). Charts are hand-written SVG; `uplot` is in `package.json` and imported nowhere. Latency windows are 1 h, 24 h and 7 d. Polling is 8 to 30 s.
7. **NetGuard** can allow a port from a `node` remote (pinned to that node's WireGuard and public /32s) or a zone of CIDRs; ICMP is already accepted by the fixed scaffold. Applying a ruleset is a plan with approval.

## Decisions

### D1. The unit is a path; checks own their paths

A **check** is the existing `Monitor`, extended: one method, one target, one or more sources, expectations, interval and an alert policy. Each (check, source) is a **path** with its own series, state and history, which is what the store already keys by. The **path set** is the existing latency configuration, renamed and generalised: one rule (sources times targets, with include, exclude and disabled pairs) that the planner expands into generated checks; there is one path set, as there is one latency configuration today. Operators can still create single checks by hand. Rejected: a new `Check` type beside `Monitor`, which would mean migrating stored rows and two result paths for one concept.

Changes to `model.Monitor` (revised after the architecture and security reviews of 2026-10-16):

- `kind` gains `icmp` (agent, unprivileged echo) and `beacon` (agent, UDP to a node's beacon).
- `target` stays a resolved string on the wire, because every deployed agent decodes it as a string and one object would fail the whole monitor list. A new optional `target_node` field names the node a target was resolved from. The server resolves it per method (beacon endpoint, public address for `icmp`, line port for `tcp`) in `MonitorsForNode` and `handleAgentMonitors` for operator checks and in the planner for generated ones, so a moved IP or a new NAT mapping follows without editing checks. Path visibility uses `target_node` instead of the `mon_lat_` id prefix.
- Sources stay the existing per-check node assignment. `control-plane` remains the source of `tls` checks only (their results keep the empty node id they have today); tcp, http and icmp from the server are not offered, because nobody asked for them and they would let a monitor admin probe the control plane's own network.
- **Capability gating.** Each agent reports the probe methods it supports in its facts. A method is assigned to a source only if that source supports it; an older agent that would report an unknown kind as a failure never receives one, and the path reads unknown with reason "agent too old for this method" instead of down.
- HTTP expectations: a status set or ranges (default 200 to 399). Optional request headers whose values are write-only secrets (stored like channel secrets, never returned), with these rules from the security review: a check with secrets must use https without skipping verification; secrets are bound to the scheme, host and port they were saved with, and changing any of those clears them; redirects are never followed on such a check (a 3xx is the answer); an edit names each header as keep, set or delete so an edit that echoes the secret-less read cannot wipe or leak them; secrets go only to the check's assigned sources, are redacted in audit diffs and are never copied into generated checks. A response body is never matched or stored; the body match of the first draft is dropped, because it turned a check into a one-bit reader of whatever the target returns.
- Destinations. Every agent check resolves its target at dial time and dials the address it checked (no second lookup). Loopback, link-local, metadata (169.254.0.0/16 and fd00:ec2::254), multicast and private ranges are refused unless the target is a node reference resolved by the server. Errors stored with results have the URL query and user info removed.
- Who may configure. Creating or editing a check or the path set needs `monitor:admin` and read access to every source and target node it names, not only to see the resulting paths.
- `packets` for `icmp` and `beacon` (1 to 10, default 5, 200 ms apart), so one run yields loss and jitter, not just one RTT. A save enforces an interval floor (10 s) and a packets-per-second budget per (source, target).
- `alert`: `off`, `down` (after N failed runs, default 2, as today) or `down_and_degraded` (adds the degraded state of D6, from M3).
- Editing. `POST /api/monitors/update` with an optimistic version, following the server's action-route style. An edit may change interval, timeout, packets, expectations, alert policy, name and sources; changing kind or target mints a new check and pauses the old one, so one series never mixes two methods. Generated checks refuse edits with 409, as delete already does; their paths are paused through the path set's disabled pairs. Pausing one source of an operator check is a new per-source paused list that both `MonitorsForNode` and result admission honour.

### D2. Methods, in order of preference for node targets

1. **beacon** when the target has an enabled beacon and the source supports it: measures the network path to the node itself, works for every node whatever lines it serves, and works through NAT because the advertised endpoint is configured per node.
2. **icmp** when it has none: kernel-answered, so nothing new listens; may be filtered by providers (D10 says when that reads unknown and when down).
3. **tcp** to a line port, today's behaviour, kept so existing paths and their history continue.

The path set picks, per source, the first method both ends support unless the operator pins one. Generated ids stay one per (target, method): `mon_lat_<target>` keeps tcp and its history, and new ids `mon_latb_<target>` and `mon_lati_<target>` carry beacon and icmp. Each generated check's node assignment is the set of sources using that method for that target, so sources can differ in method while the target is the same. The pair state gains `method` and the check id actually used.

A **path series** is addressed by (source, target node) and joins the series of every generated check for that pair by time, so the chart shows one continuous line across a method switch, marked where the method changed. No generated check with history is ever deleted except when its target node is deleted; a test pins that, because `SyncManagedMonitors` deletes history along with a monitor.

### D3. The beacon: an authenticated UDP responder that answers nothing unsigned

The operator asked for a probe-able port per agent that is convenient but safe. The strongest case against is the doctrine: Lattice's agent only dials out, and a listener is new attack surface on every node, a fingerprint that says "this host runs Lattice", and a new parser exposed to the internet. The strongest case for is that no other method measures the path to every node: line ports exist only where sing-box serves TCP, ICMP is often filtered, and NAT breaks both. The design takes the beacon, opt-in, with these properties (revised after the security review of 2026-10-16):

- **No reply to anything unsigned.** A datagram that is not exactly 96 bytes, not for a known source id, not correctly signed, not fresh, or a replay gets no reply and no log line. There is no TCP listener and no banner. An open beacon port therefore reads as open-or-filtered to a scanner, like WireGuard; it does not read as closed, because a closed UDP port draws ICMP port-unreachable from the kernel. The beacon makes no stronger claim than that.
- **No amplification.** A reply (64 bytes) is never larger than its request (96 bytes, padded); the responder reads into a 128-byte buffer and drops any datagram whose length is not exactly 96, so a longer packet with a valid prefix cannot pass.
- **Keys stay on the server.** The server mints a 32-byte key per target node and keeps it. Per epoch it derives `K_path = HMAC-SHA256(K_target, len-prefixed("lattice-beacon/v1", source_id, epoch))` for every source bound to that target, and sends the target only its table of (source id, epoch, `K_path`) and each source only its own `K_path` per target, through the authenticated config pull. Nodes hold path keys in memory only, never on disk. A stolen node config therefore yields keys for one node's paths and one epoch, and rotation (on demand as an audited action, and automatically when a source is removed from a target) ends it. Epochs N and N-1 are both accepted for two pull cycles so a rotation does not open gaps. Source ids are short exact ids assigned by the server, not hashes, so an unknown id is dropped before any HMAC is computed.
- **Request and reply.** Request: `magic "LTB1" | version | epoch | source_id | seq | sent_unix_ns | nonce(16) | padding | tag = HMAC(K_path, "req" | all prior bytes)[:16]`. The responder compares tags with a constant-time equality, accepts a request only if the timestamp is within 60 s of its clock, is not older than the responder's own start, and the nonce is not in the source's cache. Reply: `magic "LTB1" | version | status | seq | request nonce | responder_unix_ns | tag = HMAC(K_path, "rep" | all prior bytes)[:16]`; the status is ok, stale (clock), unknown epoch or rate limited, which turns silent failures into named reasons for the operator without telling an outsider anything. The source computes RTT from its own monotonic clock and drops a reply whose nonce is not one it sent.
- **Nonce cache.** Per source, at least rate times window entries (20 per second times 120 s, so 2400), inserted only after the tag verifies; when full it refuses new requests rather than evicting a nonce still inside the window, so an unauthenticated flood cannot evict anything and a compromised source can only fill its own cache.
- **Rate limits in the right order.** Before authentication the only budget is a CPU guard sized in tens of thousands of datagrams per second, kept in a fixed-size counter array (never a map keyed by attacker-chosen addresses). The tag is verified next. After authentication each source id is limited to 20 requests per second. The server also enforces, when a check is saved, a minimum interval and a packets-per-second budget per (source, target), so one operator cannot saturate a source's own budget.
- **Isolation inside the agent.** The receive loop recovers from panics (an index error on a short datagram must not kill the agent), allocates nothing on the drop path, and has a circuit breaker: if drops stay above a threshold for 60 s, the socket closes for a cooldown and the agent reports it, so the pull loop and task execution keep their CPU. A separate unprivileged process is the follow-up if the responder ever needs more than this.
- **Port and address.** Per node, the server assigns a random listen port in 40000 to 59999 (not a fixed well-known default that would land on scan lists), and the operator may override it; the save lints it against known listeners (sing-box inbounds, sshd, knock ports) and the agent reports a bind failure instead of taking a port that is in use. The agent binds the node's advertised public IPv4 only (never the wildcard, so WireGuard and private interfaces stay closed) and replies from the address a request arrived on. The advertised endpoint is an IPv4 literal and port (for a NAT node, the mapped public address and port); hostnames are refused so sources cannot be pointed at third parties or rebound to internal addresses, and sources refuse loopback, link-local and multicast endpoints. Beacon checks may only target node references, never arbitrary addresses. IPv6 is out of scope for the first version.
- **Enabling is a plan.** Turning a beacon on or off or changing its port is a plan of kind `node.beacon`, approved like other plans; the plan's hash covers the port, bind address, advertised endpoint, the source set and the limits, so what was approved is what runs. If NetGuard manages the node, the same approval carries a companion NetGuard rule set that allows the UDP port from exactly the current beacon sources (node remotes, plus each NAT source's egress address when it differs from its pinned /32) and marks the port `notrack` in both directions so spoofed datagrams cannot fill the connection-tracking table that sing-box traffic on the same node needs. Adding or removing a source later re-plans the allow set; until that plan is applied the console shows "firewall pending" for the affected paths. After enabling, one source runs a reachability check and the console shows reachable, filtered or not listening (a connected UDP socket's `ECONNREFUSED` is the "not listening" signal). Without NetGuard the port is open to the internet and protected only by the properties above; the console says so on the node page.
- **Node veto.** A new agent flag `-no-beacon`, checked before any bind and not overridable by server configuration, makes the agent refuse to listen whatever the server says and report the refusal; the beacon then reads "refused by node".

Doctrine change, applied to `docs/PRODUCT-VISION.md` with this design: the agent's control channel stays outbound-only; the one inbound socket an agent may open is the measurement beacon, which is off by default, enabled per node by an approved plan, authenticated, silent to anything unsigned and vetoable on the node.

Rejected alternatives: an HTTP or TLS endpoint on the agent (a TCP listener answers SYNs to everyone and invites a protocol stack's worth of parsing); reusing sshd or sing-box ports (the existing rule never probes sshd, and sing-box ports exist only on some nodes); ICMP only (filtered on several providers in this fleet); a raw-socket ping (needs `CAP_NET_RAW` for a root-capable agent).

The operator's "path, possibly with authentication" is covered separately by D1's HTTP checks with secret headers: any node service with a health URL can be a target from any source, under the destination rules in D1.

### D4. Retention: a week of five-minute history by default

| Tier | Resolution | Default | Setting |
|---|---|---|---|
| Raw results | every run | 1440 rows per path (24 hours at 60 s), as today | none |
| Fine rollups | 5 minutes | 7 days | 3 to 14 days |
| Coarse rollups | 1 hour | 35 days | none |

The operator asked for at least three days, extendable to seven; the fine tier covers that at five-minute resolution, which is about 2000 points per path over a week, more than a chart can draw. Rejected: one-minute rollups (four times the size for detail the raw tier already holds for a day), a 90-day coarse tier and a 30-day fine setting (nobody asked, and they dominate the size), and moving monitor history into metricsdb (its buckets keep min, max and average, which cannot answer p95 or jitter).

Bucket contents. The existing rollup already keeps count, failures, min, max and a latency histogram from which p50 and p95 are derived, so percentiles need no new work. M1 adds, as additive JSON fields with no migration: the sum and count of absolute differences between consecutive successful samples (jitter, computed at ingest from the last successful latency kept in the path's latest record, so merged buckets stay exact) and, from M2a, packets sent and lost. The histogram counts runs; a multi-packet run contributes its median RTT. Loss is lost over sent when packets were sent, otherwise failed runs over runs.

Pruning. No compaction pass exists today: rollups are trimmed only when a pair opens a new bucket and raw rows only when a row is inserted, so paused paths, sources removed from a check and paused generated checks never trim. M1 adds an hourly sweep that deletes buckets and rows below each tier's cutoff for every pair, in bounded transactions. bbolt reuses freed pages but never shrinks its file, so lowering retention frees space for reuse, not disk; the settings page says so before saving.

Size, measured from the encoding (key 84 bytes, fine value about 85 to 110 bytes with the new fields, about 200 bytes logical and 260 to 400 on disk after page splits): 100 paths cost about 6 MB of fine rollups per day of retention, so about 40 MB at the 7-day default, plus about 7 MB of coarse rollups and about 26 MB of raw rows. A full mesh of 25 nodes (600 paths) is about 250 MB fine at 7 days, 45 MB coarse and 160 MB raw. The settings page shows the measured size from bucket statistics and the projected size for the chosen retention, and warns above 300 paths at intervals under 30 s.

### D5. One series API for every path

Routes stay under `/api/monitors/` in the server's action-route style.

- `GET /api/monitors/paths?window=` returns the matrix: sources, targets, and per path the current state, method, p50, p95, jitter, loss, samples and expected for the window, the delta against the same window one period earlier, and the reason when unknown. Windows: 1h, 6h, 24h, 3d, 7d, and 14d when fine retention allows. Windows of 3 days and longer read coarse buckets for the matrix; each window's result is cached until its next bucket closes.
- `GET /api/monitors/series?source=&target_node=&window=` (or `monitor=&source=` for an operator check) returns buckets `{t, n, fail, sent, lost, min, p50, p95, max, jitter, method}`. The step is the smallest multiple of the finest covering tier's resolution that gives at most 720 points, merged on the server: 1h raw, 24h 5-minute (288), 3d 10-minute (432), 7d 15-minute (672), 14d 30-minute (672). Missing buckets are explicit. It replaces the latency-only series route, which stays as an alias for one release.
- `GET /api/monitors/settings` and `POST /api/monitors/settings/update` (versioned) for retention, with measured and projected size.
- Beacon: `GET /api/nodes/beacon?node_id=` (state, port, advertised endpoint, key epoch, last authenticated request seen, refusal) and plan creation for `node.beacon`.

History reads run in a bolt read transaction outside the store's global mutex, as a note in `store/monitor_results.go` already proposes, so a 7-day matrix cannot stall ingest or the rest of the store.

Scopes stay `monitor:read` and `monitor:admin`; a path is visible only if the caller can read both its source and its target node, as latency data is today. Beacon plans need the node's admin scope in addition, because they open a port.

### D6. States, triangulation and alerts

A path is **up**, **degraded** (from M3), **down** or **unknown**. Down follows the alert policy (N failed runs). Unknown means no result when one was expected, with the reason (agent offline, source paused, agent too old for the method, method refused by the node, ICMP filtered, beacon not enabled, firewall pending); unknown is never drawn green.

Degraded, evaluated on a server schedule every minute, not on console polls, and only once a path has 24 hours of baseline: loss over the last hour, with at least 30 samples, above both 2 percent and twice the path's 7-day loss; or p50 over the last 15 minutes above both twice its 7-day p50 and its 7-day p50 plus 30 ms. Entering needs the condition on two consecutive evaluations and leaving needs it absent for ten minutes, so a single dropped probe on a China path does not flap. The 7-day baselines are cached and refreshed hourly. Thresholds are per check settings with those defaults.

With more than one source, the console **triangulates**: a target down from at least two fresh sources and from every fresh source reads as "the target is unreachable"; a source failing at least three targets and most of its targets reads as "this source's network"; anything else reads as "this path". With today's single source the verdict is always "this path", which is honest. The verdict is a label in the attention list with its evidence; it is never an alert by itself.

Alerts reuse the notification catalogue (design notify section 13): `monitor.down` and `monitor.recovered` as today for operator checks; new types `path.degraded` and `path.recovered` (category monitoring, severity warning and recovered) for a path set whose policy is `down_and_degraded`. The path set defaults to `off` for alerts, matching today's behaviour of not paging on latency checks, so turning this on is the operator's choice. `pendingIncidents` (`server_incidents.go`) does not skip managed latency monitors the way the pager does; M1 adds that skip and a test.

### D7. Console: structure

Layers of Monitoring, in this order, with Overview as the default:

1. **Overview.** Proof line (observed time, paths, and counts of down and unknown, plus degraded from M3; a state the server does not compute yet is not shown). Attention list, worst first, carrying the triangulation verdicts. A compact "fleet reach" strip: for each source, how many of its targets are up, degraded, down, unknown. Links into Paths filtered to the item.
2. **Paths.** The matrix, targets as rows grouped by region (as the Latency layer groups today), sources as columns. Each cell shows the window p50 as a number, toned by state; loss above zero adds a small loss figure under it; unknown is hatched with the reason on hover and focus. Window control (1h, 6h, 24h, 3d, 7d, and 14d when retention allows) shared by the whole page through `?window=`. A filter field using the console's list query syntax (`target:jp state:degraded source:cd-hs-sh`). Selecting a cell opens the path sheet.
3. **Checks.** Every check in one list: operator checks and, grouped under the path set, its generated checks. Create and edit in an object sheet (D9). The path set is edited here too; this replaces the "Probe settings" sheet of the Latency layer.
4. **Topology.** Kept, fed by the same matrix data; with several sources it draws one fan per source and lets the operator pick which sources to show.
5. **Incidents.** Unchanged.

The old Latency layer becomes Paths; `?view=latency` redirects to `?view=paths` for one release. The node page gains a Paths card with two lists, "reaches" (paths from this node) and "reached by" (paths to it), each row with the window p50 and state, and a Beacon card (state, port, advertised endpoint, last seen request, enable or change through a plan).

### D8. The path sheet and the chart

The path sheet is the place the operator reads fluctuation, so it carries the page's one strong visual: the **path chart**.

- One time axis, two lanes sharing it. The upper lane plots latency: the band from min to p95 as a light fill (the histogram yields p50 and p95; a lower percentile would add storage for little reading value) in the state tone, the p50 as a line in the foreground ink, min and max as faint ticks only when zoomed to raw or 5-minute buckets. The lower, short lane plots loss per bucket as bars (zero draws nothing). Missing buckets are hatched across both lanes and labelled "no data" with the reason; they never interpolate.
- Threshold guides for the degraded rule (the 7-day p50 and the trigger level) as dashed lines, labelled once.
- A crosshair with the exact bucket values (time, p50, p95, jitter, loss, samples of expected, method) that follows pointer and keyboard (left and right arrows step buckets); drag selects a range and zooms; double-click or Escape resets.
- "Compare with the previous period" overlays the previous window's p50 as a thin dotted line.
- Above the chart, a stats row for the window: p50, p95, jitter, loss, availability (successful runs of expected), samples of expected. Below, the latest raw runs (time, RTT per packet, error) and the method, target endpoint and source.
- Actions: pause this path, edit the check, open the source or target node.

The chart uses uPlot (already a dependency, canvas, handles 10,000 points with a cursor) wrapped in one console component with the console's tokens; sparklines elsewhere stay SVG. The colour rule is the console's: state tones are the only saturated colour; the band is the state tone at low opacity; p50 is foreground ink so it reads in every state. Below 768 px the sheet is full screen, the chart spans the width with fewer ticks, and the crosshair values sit in a fixed row above the chart so the finger does not cover them.

### D9. Console: checks editor

An object sheet with the form in task order: what to measure (method, with one sentence each: "Beacon: the path to the node itself; needs the node's beacon", "ICMP: ping; some providers filter it", "TCP: connect to a port", "HTTP: request a URL and check the answer", "TLS: certificate expiry, from the control plane"), from where (sources: node picker with region groups, each node showing the methods its agent supports; `control-plane` only for TLS), to where (a node, resolved per method and shown resolved, or an address or URL), expectations (per method), how often (interval, timeout, packets) and what to do when it fails (alert policy). The sheet shows the resolved endpoint for every source before saving, and refuses with the reason when a node target cannot be resolved for the chosen method (no beacon, no TCP line, no public address). The path set uses the same sheet with a target rule instead of a single target, and previews the paths and the method each source will use.

Saving a check or the path set is an audited configuration change, as monitor configuration is today; enabling a beacon is the only part that goes through a plan, because it opens a port.

### D10. Agent changes

- `icmp` prober using unprivileged datagram echo (`udp4` ICMP sockets) with a fixed 32-byte payload carrying 16 random bytes per echo; a reply counts only if its payload and source address match, so an off-path host cannot forge "up" by guessing the kernel's id and sequence. If the kernel's `net.ipv4.ping_group_range` excludes the agent's group, the result is unknown with reason `icmp_not_permitted` and the agent reports the capability once in its facts. All-loss on a path that has never succeeded reads unknown ("may be filtered"); all-loss for the alert policy's run count on a path that has succeeded before reads down, so a node that really dies still alerts. The same interval floor and per-target packet budget as beacons apply.
- `beacon` prober (client) and responder (server side of D3), both in a new package with: a fuzz test of the request parser that fails on any panic; a test that replies are never larger than requests and that a 97-byte datagram with a valid 96-byte prefix gets no reply; tests that wrong tags, stale timestamps, timestamps before the responder started, unknown source ids, unknown epochs and replayed nonces get no reply; an `AllocsPerRun == 0` test on the drop path; and a circuit-breaker test.
- The server keeps refusing results for checks not assigned to the authenticated node and results that claim another source (verify the existing ingest does this; add a test either way).
- Multi-packet runs for both, reporting per-packet RTTs, lost count and the run's jitter.
- Result queue kept in memory, unchanged; the server already refuses stale results.
- The `-no-beacon` flag and a capability line in `-compat-json`.
- Each agent reports the probe methods it supports in its facts (D1 capability gating).
- The SDK `MonitorResult` and the stored row gain sent, lost and a bounded per-packet RTT list (at most 10).
- A node-agent prerelease, rolled out through the normal approved update path.

### D11. M2a wire contract

Added 2026-10-16 with the SDK change that carries it (lattice-sdk `feature/20261016_monitoring-paths-m2a`). The agent, the server and the console build against this section. Every field is additive and omitted from JSON until set, so a deployed agent decodes the monitor list it always did and an older server ignores what a newer agent reports. The shared rules (status sets, header rules, origins, destination refusal, probe methods) are functions in `model/monitor_checks.go`, so the server and the agents apply one implementation.

**Capability facts.** The agent adds two top-level keys to the body of every `POST /api/agent/hello` and every heartbeat (`/api/agent/metrics`), beside `capabilities`:

| Key | Type | Meaning |
|---|---|---|
| `probe_methods` | list of strings | The monitor kinds this agent runs on this host now: `tcp`, `http`, `icmp` (and `beacon` from M2b). An M2a agent always lists `tcp` and `http`. |
| `probe_refusals` | object, kind to reason code | Kinds the agent implements but the host refuses, for example `{"icmp": "icmp_not_permitted"}` when `net.ipv4.ping_group_range` excludes the agent's group. A refused kind is not in `probe_methods`. |

The server replaces both on every hello and heartbeat and stores them on the node as `Node.ProbeMethods` and `Node.ProbeRefusals` (persisted, so they survive a server restart). An absent or empty `probe_methods` means an agent older than M2a, which runs exactly `tcp` and `http` (`model.EffectiveProbeMethods`). Unknown kinds are dropped. Node reads (`GET /api/nodes` and the node view) carry `probe_methods` as the effective list and `probe_refusals` as stored.

**Gating.** The server hands a source a check only if the check's kind is in the source's effective methods, and an http check with a status set other than the default or with any header only to a source that reports `probe_methods` at all, since an older agent would judge it by the old rule and send it without its headers. `GET /api/agent/monitors` and the path matrix apply the same rule. A path whose source does not run its kind reads unknown with reason `agent_too_old`, or with the refusal's code when the kind is in `probe_refusals`. It never reads down for that reason. An M2a agent that is still handed a kind it does not know reports a result with reason `agent_too_old` and no failure.

**Check fields** (`model.Monitor`):

| Field | JSON | Kinds | Bounds and default | Set by | Read by |
|---|---|---|---|---|---|
| TargetNode | `target_node` | icmp, tcp | an existing node id | operator on create (immutable on edit), planner on generated checks | server resolution, visibility; agents only to skip the private-range refusal |
| Target | `target` | all | icmp: an IPv4 literal; tcp: host:port; http: URL | operator, or the server when `target_node` is set | agents dial it |
| Packets | `packets` | icmp | 1 to 10, zero reads as 5; echoes 200 ms apart | operator, planner (5) | agents |
| ExpectStatus | `expect_status` | http | comma list of codes and ranges 100 to 599, at most 16 entries; empty reads as `200-399`; stored canonical (sorted, merged) | operator | agents |
| Headers | `headers` | http | at most 8, `{name, value, secret, set}`; names are tokens up to 64 bytes, unique without regard to case, stored canonical (`X-Api-Key`); values 1 to 4096 bytes, no control characters but tab; `Host`, `Content-Length`, `Transfer-Encoding`, `Connection`, `Keep-Alive`, `Upgrade`, `TE`, `Trailer`, `Expect` and every `Proxy-*` are refused | operator | agents |
| SecretsOrigin | `secrets_origin` | http | `scheme://host:port`, lower case, port always written (`model.MonitorOrigin`) | server, whenever any header is secret | agents |

**Resolution of `target_node`.** The server resolves per kind each time it hands a check to an agent (operator checks in the agent monitor list, generated checks in the planner every two minutes), so a moved address or a new line follows without an edit. icmp resolves to the node's public IPv4. tcp resolves to the node's public TCP line port by the rule the latency planner already uses (never SSH, never a knock-gated port). A check whose node cannot be resolved for its kind is refused on create with the reason, and is left out of the agent's list later, its paths reading unknown with `not_probeable`. http does not take `target_node` in M2a; beacon adds its own resolution in M2b.

**Generated checks.** The path set (the latency configuration) gains `method` (`""`, `tcp`, `icmp` or `auto`; empty reads as `tcp`, so a stored configuration keeps today's paths and history) and `source_methods` (source node id to the same values, overriding `method`). `auto` picks per source the first kind both ends support: icmp when the source runs it and the target has a public IPv4, else tcp when the target has a TCP line. A pin never falls back: a pinned icmp pair whose source does not run icmp reads unknown `agent_too_old`. Generated ids are `mon_lat_<target>` for tcp (unchanged) and `mon_lati_<target>` for icmp; each is assigned the sources that use its kind for that target, carries `target_node`, never carries headers, and is kept paused with its history while no source uses it. The pair state gains `method` and `reason`; the plan's node gains `icmp_target` and `icmp_monitor_id`. A target whose enabled pairs are all held by their sources' methods reads paused with target reason `source_method` (added in lattice-sdk da0390e). The path series by (source, target node) joins both ids and marks the switch in `method_changes`.

**Validation on save** (create, edit, and the path set):

- Creating or editing a check or the path set needs `monitor:admin`, admin on every source, and `monitor:read` on every node it names as a target.
- icmp: the target is a node reference or a global IPv4 literal. The interval floor is 10 s, and a run, (packets minus 1) times 200 ms plus the timeout, must end before the next one starts. Per (source, target address), the packets per second of every enabled icmp check together, operator and generated, packets over interval summed, may not exceed 2.
- tcp: a node reference, or host:port whose host is a name or a global IP literal.
- http: an absolute http or https URL with a host and no user info; a literal host must be global, and `localhost` and names under `.localhost` are refused. A check with any secret header must use https. There is no skip-verify option, so certificates are always verified.
- A host whose last label is a number (`2130706433`, `127.1`, `0x7f.1`) is refused, because some resolvers read it as an address and no DNS name ends in a number; so is a host with a zone. An edit does not judge the stored target again, so a check saved before these rules stays editable; the agent still refuses its destination at dial time.
- Destination refusal (`model.MonitorDestinationRefused`, lattice-sdk c9739fa): loopback, link-local, metadata (169.254.0.0/16, fd00:ec2::254), multicast, private (RFC 1918, fc00::/7), carrier-grade NAT (100.64.0.0/10), 0.0.0.0/8, 192.0.0.0/24, 192.88.99.0/24, 198.18.0.0/15, 240.0.0.0/4 (broadcast included) and unspecified; NAT64 (64:ff9b::/96), 6to4 (2002::/16) and IPv4-translated (::ffff:0:0:0/96) addresses judged by the IPv4 address they embed; local-use NAT64 (64:ff9b:1::/48), IPv4-compatible (::/96), site-local (fec0::/10), Teredo (2001::/32) and discard-only (100::/64) refused outright (lattice-sdk f268902). Documentation ranges stay allowed for monitors. An IPv4-mapped address is judged as IPv4 and a zone never changes the verdict. A node reference resolved by the server is exempt at the agent; the server judges the node's public address by the same rule when it resolves it.
- `packets` only on icmp, `expect_status` and `headers` only on http; tls takes none of them.

**Secret headers.**

- A secret header's value is encrypted at rest as notification channel secrets are, and every response the server gives (create, edit, list, audit) carries `{"name", "secret": true, "set": true}` with no `value`. Plain headers are returned with their value. Audit records name the headers that changed, never a value.
- Only the agents assigned the check receive values, in `GET /api/agent/monitors`. Generated checks never carry headers.
- Secrets are bound to `secrets_origin`. Because a check's target cannot change on edit (a new target is a new check), a new origin always starts without secrets; the console cannot carry them across because it never holds them.
- Edits use `MonitorUpdate.headers`, a list of `{name, op, value, secret}` applied in order. `keep` asserts the header exists (the edit is refused when it does not, so a stale editor notices). `set` adds the header or replaces its value and secrecy and needs a value. `delete` removes it and is a no-op when it is absent. A header the list does not name is kept, and a name may appear once per edit. Absent or empty leaves the headers unchanged. An echoed read therefore can neither wipe nor leak a secret.

**What the agent enforces.**

- Every kind: resolve the target once, judge every address with `MonitorDestinationRefused` unless `target_node` is set, refuse the run when any address is refused, and dial only an address it judged (no second lookup, no proxy from the environment). A refused run reports reason `destination_refused`.
- http: GET only. Redirects are never followed for any http check; a 3xx is the answer and is judged against `expect_status`. Latency is the time to the response headers, and the body is closed unread. Secret headers are sent only when the request's origin equals `secrets_origin` and the scheme is https; otherwise the run reports `destination_refused` without sending anything. Error text never carries a header value.
- icmp: unprivileged `udp4` echo sockets, `packets` echoes 200 ms apart, a fixed 32-byte payload carrying 16 random bytes per echo, and a reply counts only if its payload and source address match. Each echo waits `timeout_sec`. When the kernel refuses the socket, the run reports `icmp_not_permitted` with `sent` zero, and the agent moves icmp to `probe_refusals`.
- Error text: URL user info and query are removed. The server removes them again before storing. This is a second layer, not a promise: a token belongs in a secret header, never in a URL, because the URL is returned to everyone who can read the check.

**Results** (`model.MonitorResult`):

| Field | JSON | Meaning |
|---|---|---|
| Sent | `sent` | echoes sent by a multi-packet run, 1 to 10; zero for tcp and http |
| Lost | `lost` | echoes with no matching reply, 0 to `sent` |
| RTTsMs | `rtts_ms` | RTT of each echo that came back, in send order; length `sent` minus `lost`, at most 10 |
| LatencyMs | `latency_ms` | a multi-packet run's median RTT (mean of the two middle values when even) |
| Success | `success` | for a multi-packet run, true when at least one echo came back |
| Reason | `reason` | a code (`[a-z0-9_]`, at most 40) for a run that could not measure the path: `agent_too_old`, `icmp_not_permitted`, `destination_refused`; `success` is false |

tcp and http results carry `sent` 0 and no `rtts_ms`; the server counts each such run as one probe. An icmp run that fails before any echo leaves (a lookup or socket error other than permission) carries `success` false, `sent` 0, an error and no reason, and is an ordinary failed run. `cert_not_after` is tagged `omitzero` and is absent unless a tls handshake read a certificate. The server refuses a result whose packet fields are out of bounds or inconsistent and zeroes them on single-probe kinds. The batch route decodes entries one by one: an entry that does not decode or fails the bounds is listed in `dropped` with reason `invalid` and the rest of the batch is stored, because an agent drops the whole batch on a 400. It keeps refusing results for checks not assigned to the authenticated node, and a result that names another node is now dropped as `wrong_node` instead of being rebound to the posting node. A result with a reason is stored raw and as the pair's latest, counts as neither success nor failure in rollups and fail streaks, and makes the path read unknown with that reason while it is the latest.

**Rollups and reads.** Buckets gain `sent` and `lost`, counting probes: every echo of a multi-packet run, and one per run of tcp or http. Loss is `lost / sent` where `sent` is above zero, and `fail / n` in buckets written before M2a. A multi-packet run counts once in `n`, and its median RTT enters the histogram and the jitter figure (the difference between consecutive successful runs, as in M1). Series buckets carry `sent` and `lost`.

**States and reasons.** New unknown reasons: `agent_too_old`, `icmp_not_permitted`, `icmp_filtered`, `destination_refused`. icmp all-loss runs on a path that has never had an echo back read unknown `icmp_filtered` and do not page. Once a path has succeeded, all-loss runs count as failures, so `alert_after` of them in a row read down and page as any other failure.

### D12. M2b wire contract

Added 2026-10-16 with the SDK change that carries it (lattice-sdk `feature/20261016_monitoring-paths-m2b`, package `beacon` and `model/beacon.go`; revised the same day after the M2b security and Go reviews, with no field renamed). The agent, the server and the console build against this section. Every field is additive and omitted from JSON until set, so a deployed agent decodes the config and the monitor list it always did. The wire format is one implementation in package `beacon`, which the server, the agents and their tests import; nothing here is to be re-implemented.

**Datagrams.** Integers are big-endian. A request is exactly 96 bytes and a reply exactly 64, so a reply is always smaller than its request.

| Request offset | Bytes | Field |
|---|---|---|
| 0 | 4 | magic `LTB1` |
| 4 | 1 | version, 1 |
| 5 | 4 | epoch, above zero |
| 9 | 4 | source id, above zero |
| 13 | 4 | seq |
| 17 | 8 | sent, unix nanoseconds, signed |
| 25 | 16 | nonce, random per request |
| 41 | 39 | padding, zero |
| 80 | 16 | tag: HMAC-SHA256(K_path, `req` followed by bytes 0 to 79), first 16 bytes |

| Reply offset | Bytes | Field |
|---|---|---|
| 0 | 4 | magic `LTB1` |
| 4 | 1 | version, 1 |
| 5 | 1 | status: 0 ok, 1 stale, 2 unknown epoch, 3 rate limited |
| 6 | 4 | seq, copied |
| 10 | 16 | nonce, copied |
| 26 | 8 | responder clock, unix nanoseconds |
| 34 | 14 | padding, zero |
| 48 | 16 | tag: HMAC-SHA256(K_path, `rep` followed by bytes 0 to 47), first 16 bytes |

**Keys.** The server mints a 32-byte key per target node when a plan first enables its beacon, stores it encrypted at rest as notification channel secrets are, deletes it when a plan disables the beacon, and never sends or logs it. `K_path = HMAC-SHA256(K_target, lp("lattice-beacon/v1") | lp(source_id) | lp(epoch))`, where `lp(x)` is x's length as 4 bytes followed by x and the ids are 4-byte integers (`beacon.DerivePathKey`; the test vector for target key bytes 0x01 to 0x20, source 3, epoch 7 is `95d783026533fad67f52bd4556f8f5a16f4067f379b7663a37082a0a784344a8`). Source ids are assigned by the server, one per node, starting at 1; no id number is ever given out twice, and deleting a node drops its id and its place in every approved set, so a machine enrolled later under the same node id is a new source that needs its own approval. The epoch is a per-target counter starting at 1 that never goes back, even across a disable.

**Responder decisions** (`beacon.Responder.Handle`, in this order): length not exactly 96, wrong magic or version, padding not zero, unknown source id and unknown epoch all drop before any HMAC is computed; a tag that does not verify (constant-time comparison) drops; then a retired epoch answers `unknown_epoch`, a timestamp more than 60 s from the responder's clock either way or before the responder's start answers `stale`, a nonce already in the source's cache drops, a full nonce cache or a source over 20 requests per second answers `rate_limited`, and anything else answers `ok`. The nonce is cached before the rate decision, so a request refused for rate cannot be replayed into a later budget, and held one nanosecond past the last instant its request is fresh. `LastAuthenticated` moves only for a fresh, new request whose tag verified, so a captured request replayed later cannot keep it fresh. The reply's nonce is copied out of the request first, so `out` may share the read buffer. A non-ok reply is signed, goes only to a request whose tag verified, and is sent at most once per second per source id, so a captured request replayed after it went stale draws at most one 64-byte reply a second. The nonce cache holds at most 2400 unexpired nonces per source (20 per second for 120 s), each until its request's sent time plus 60 s, refuses rather than evicts when full, and is keyed by a seeded hash. Nothing on a drop path allocates (`AllocsPerRun` is zero in the SDK tests). Handle is single-goroutine; `SetTable` may run beside it (and beside itself; it is serialized) and keeps a source's nonce cache and rate state across a table refresh.

**What the agent adds around Handle.** A UDP socket bound to exactly `bind:port` (never the wildcard) and read into a 128-byte buffer; a pre-authentication CPU guard counted in a fixed-size array, never a map keyed by addresses; panic recovery around each datagram; the circuit breaker of D3 (drops above a threshold for 60 s close the socket for a cooldown, state `circuit_open`); keys in memory only; and the `-no-beacon` flag, checked before any bind and not overridable by configuration, which makes the agent report `refusal: "refused_by_node"` and state `refused` and never bind.

**Config pull.** `GET /api/agent/config` gains `beacon` (`model.AgentBeaconConfig`):

| Key | Type | Meaning |
|---|---|---|
| `source_id` | integer | this node's source id, sent in every request |
| `keys` | list of `{target_node, epoch, key}` | this node's path key per target it may probe by beacon, for the epoch to send with now; `key` is 32 bytes, base64 |
| `responder` | `{bind, port, limits, table}` | present only while an applied plan enables this node's beacon and the agent reports a responder without refusal; absent means close any socket |
| `responder.table` | list of `{source_id, epoch, key, retired}` | the path keys this node accepts, at most two epochs per source |
| `responder.limits` | `{source_rate_per_second, min_interval_sec, packets_per_second_max}` | 20, 10, 2 in v1 |

A target receives only its own table and a source only its own key per target; a test pins both. Keys go to a source only for targets whose applied plan approved it and that it currently uses by beacon (the table is the approved set intersected with the current set).

**Rotation.** Rotating from N-1 to N adds N to the target's table beside N-1. Sources switch to N 20 s after the target first pulls a table holding N (two default pull cycles), so the target holds a key before any source uses it. N-1 stays accepted for 2 minutes after that pull, then stays 10 minutes as retired (answering only `unknown_epoch`), then leaves the table. A rotation during another one's overlap drops the oldest epoch at once. The server rotates on `POST /api/nodes/beacon/rotate` (an audited action) and automatically whenever a source leaves the target's table (a pair disabled, a source removed from the path set or a check, a node deleted or disabled, a change plan that approves fewer sources).

**Facts.** Every hello and heartbeat body gains the top-level key `beacon` (`model.BeaconFacts`) beside `probe_methods`: `responder` (the agent implements the responder), `refusal` (`refused_by_node` under `-no-beacon`), `state` (`off`, `listening`, `bind_failed`, `circuit_open`, `refused`), `bind`, `port`, `epoch` (newest in the applied table), `sources` (source ids in it), `last_auth_at` (`Responder.LastAuthenticated`: the last fresh, new request whose tag verified) and `error` (at most 200 bytes; the server replaces control characters). The beacon client is reported as `beacon` in `probe_methods`; it only sends, so `-no-beacon` does not touch it. The server replaces the report on every hello and heartbeat (a body without `beacon` clears it, as one without `probe_methods` clears those) and stores it as `Node.Beacon` without `last_auth_at`, which it keeps in memory so probing a beacon never rewrites the state file.

**The beacon check.** Kind `beacon`, always with `target_node` and never an operator address: the server resolves `target` to the target's advertised endpoint each time it hands the check out. `packets` 1 to 10 (zero reads as 5), 200 ms apart, each request waiting `timeout_sec`; interval at least 10 s with the run ending before the next starts; per (source, target node) the packets per second of every enabled beacon check together may not exceed 2. A save refuses a target without an applied, enabled beacon. The source refuses an endpoint `beacon.ParseEndpoint` refuses (reason `destination_refused`), uses one connected UDP socket per run, a fresh random nonce per request, measures RTT on its monotonic clock and drops any reply that does not verify or whose nonce it is not waiting for. Results use D11's fields: `sent` is the packets sent, `lost` those without an ok reply, `rtts_ms` the ok ones. A run with no ok reply carries a reason when it learned one: `beacon_not_listening` when the socket read `ECONNREFUSED`, else `beacon_stale`, `beacon_unknown_epoch` or `beacon_rate_limited` from a signed reply; `beacon_no_key` with `sent` 0 when the source holds no key for the target. A run that only lost packets carries no reason and is an ordinary failure.

**Endpoint, bind and port.** The advertised endpoint is an IPv4 literal and port: the node's public IPv4 and listen port by default, a NAT port mapping when the operator sets one. Host names, IPv6, 0.0.0.0/8, loopback, link-local (which holds metadata), multicast and 240.0.0.0/4 with broadcast are refused (`beacon.ParseEndpoint`). The endpoint's address must also be one of the node's own: its public IPv4, its primary interface address, or an address of a public line endpoint the latency port rule accepted for it (which covers a provider edge it declares). The server judges that at every render of a plan and every time it hands out a key or a check, so no plan can point sources at a third party, and a node that moves off the address is no longer probed there (its paths read `not_probeable` until a change plan). The bind address follows the same rule and defaults to the node's primary interface address (its private address on a NAT node), else its public IPv4. The server assigns each node a random listen port in 40000 to 59999 once and keeps it; an operator may choose any port from 1024 to 65535.

**The node.beacon plan.** `POST /api/nodes/beacon/plan` with `model.BeaconPlanRequest` (`node_id`, `action` of `enable`, `disable` or `change`, optional `port`, `bind`, `endpoint`) answers `{approval, plan, findings}`. The approval has plugin `beacon` and action `node.beacon`; its plan is `model.BeaconPlan` as indented JSON: the resulting settings (enabled, port, bind, endpoint, limits), the previous ones, the source set (each node with its source id and, under NetGuard, the /32s it may come from), the exposure (`netguard` or `internet`), the NetGuard companion (port, allow set, `notrack`, binding version, the whole ruleset and its SHA-256) and the base version. Approving needs the plan's SHA-256 as every hashed approval does, and the server re-renders the plan from live state at the decision and refuses it as stale when the bytes differ or another plan applied since its base version, so a change to any covered field invalidates the approval; the decision also runs the lint again, since a listener may have taken the port in between. Reading the approval needs `monitor:read` on every source it names, since it carries their addresses. Planning and deciding need `monitor:admin` and `node:admin` on the node, `network:plan` to plan and `network:apply` to decide, and `netguard:admin` as well when the plan carries a companion. Findings block on a port a sing-box inbound, sshd, a knock sequence or WireGuard uses, and on a bind address that is the node's WireGuard address; they warn on a bind address that is not the node's primary or public address, a mapped endpoint, no sources yet, and a node NetGuard does not manage (the port is then open to the internet and protected only by D3's properties, which the node page says).

**The source set and NetGuard.** The current source set of a target is every path set source whose method for it is `auto` or `beacon` and that runs the beacon client, with the pair enabled, plus every source of an enabled operator beacon check naming it. The approved set is the applied plan's. When NetGuard manages the node, the companion admits UDP to the beacon port from exactly the approved sources (each source's public and WireGuard /32s, plus the egress IPv4 the server sees the source connect from when that is a global address different from both) and marks the bind address and port `notrack` on the way in (`ip daddr` and destination port, in a prerouting chain at raw priority) and on the way out (`ip saddr` and source port, output at raw priority), so forwarded traffic and other local addresses stay tracked; nftables 1.0.6 (Debian 12) accepts and applies the chains, and the agent's managed-table hash covers them. Until the companion's apply task succeeds, the beacon stays closed to every source (`firewall_pending`, no keys, no beacon checks, no reachability check), and it stays closed when the task fails. The companion stays in the node's NetGuard compile input, so a later NetGuard plan keeps it as approved. When the current set differs from the approved set, the beacon view says `firewall_pending` and a current source outside the approved set reads unknown `firewall_pending`, or `beacon_source_pending` when NetGuard does not manage the node; either way the target holds no key for it until a change plan is applied.

**Method preference** (the path set, D2). `beacon` joins `method` and `source_methods`. `auto` picks per source and target: beacon when the target's applied plan enables its beacon and approved this source, the source runs the beacon client, and the target's agent neither refuses the beacon nor lacks a responder; else icmp when the source runs it, the target has a public IPv4 and icmp does not read `icmp_filtered` for that pair (the console design review decision of 2026-10-16: a pair whose latest icmp result is that verdict stays on tcp, so the series does not flap, and tries icmp again once that result is a day old); else tcp when the target has a TCP line. A pinned method never falls back. Generated beacon checks are `mon_latb_<target>` with five packets, carry `target_node`, and are assigned the sources that use beacon for that target; the plan's node gains `beacon_target` and `beacon_monitor_id`; the path series by (source, target node) joins `mon_lat_`, `mon_lati_` and `mon_latb_` and marks each switch in `method_changes`.

**Reachability check.** When a plan that enables or changes a beacon is applied and the target reports `listening` on the planned address and port, the server hands one approved, online source running the beacon client a generated check `mon_beaconr_<target>` (managed by `beacon`, three packets, 60 s) until its first result, then pauses it and stores the verdict: `reachable` when a reply came back, `not_listening` on `beacon_not_listening`, `filtered` when every request was lost, `no_source` when no source could run it. It is not a path and is left out of the matrix.

**Reads.** `GET /api/nodes/beacon?node_id=` (`monitor:read` and read access to the node) answers `model.BeaconView`: `state` (`off`, `pending`, `listening`, `refused_by_node`, `not_listening`, `agent_too_old`) with a reason, the applied settings and approval, the current epoch and when it rotated, `last_auth_at`, the agent's facts, the reachability verdict, the exposure, `firewall_pending`, each source with whether it is approved and current, an open plan's approval id and the suggested port. It never carries a key, and neither does any audit record.

**States and reasons.** New unknown reasons, all paths: `beacon_not_enabled` (the target has no applied, enabled beacon), `firewall_pending`, `beacon_source_pending`, `refused_by_node`, `beacon_not_listening` (from the target's facts or a source's result), `beacon_filtered` (every request of every recent run lost on a path that has never had a reply; once it has, all-loss reads down, as icmp does), and from signed replies `beacon_stale`, `beacon_unknown_epoch` and `beacon_rate_limited`, plus `beacon_no_key` from a source. They are prefixed with `beacon_` where a bare word (stale, rate limited) would collide with other parts of the console. An operator beacon check whose target's beacon was disabled reads `beacon_not_enabled`.

### D13. M3 wire contract

Added 2026-10-16, before the code, as the contract every M3 lane builds against: lattice-sdk, lattice-server and lattice-dashboard on branches named `feature/20261016_monitoring-paths-m3`, read against the integration heads that hold M1, M2a and M2b (sdk 82a79eb, server 36b692e, dashboard d365ade). M3 changes no agent and needs no agent prerelease: everything below is computed by the server from history the hot store already keeps, or by the console from the matrix. Every new field of a check or the path set is additive and omitted from JSON until set, so a stored check or path set decodes as it did; the two new read fields, `degraded_at` on the matrix and `baseline` on a series, are always present on an M3 server (null when there is nothing to say), which is how the console tells an M3 server apart. The server and the dashboard ship together as one server image with the SDK pin bumped in the same slice. Where this section and D6 to D9 differ, this section is the settled one.

**The degraded rule.** One rule for every path whose check kind is `tcp`, `http`, `icmp` or `beacon`. A `tls` check measures a certificate, runs on the control plane at long intervals, and is never evaluated; `down_and_degraded` and `degraded` are refused on it. The constants live in `model/paths.go`; the four thresholds are settings (next paragraph).

| Constant | Value | Meaning |
|---|---|---|
| `PathDegradedEvery` | 1 minute | the evaluator's schedule, on a server ticker, never on a console read |
| `PathBaselineSpan` | 7 days | the baseline window: the one-hour buckets whose start lies in [H minus 7 days, H), where H is the current hour (`now.Truncate(1h)`), so the baseline holds whole hours only |
| `PathBaselineMinHours` | 24 | a path is judged only once its baseline window holds at least 24 one-hour buckets with at least one countable run (the "24 hours of baseline" of D6); until then it is never degraded |
| `PathDegradedLossWindow` | 1 hour | loss over the raw rows stamped in [now minus 1 h, now] |
| `PathDegradedMinProbes` | 30 | the loss arm needs at least 30 probes in that hour |
| `PathDegradedLatencyWindow` | 15 minutes | p50 over the raw rows stamped in [now minus 15 min, now] |
| `PathDegradedMinLatencyRuns` | 5 | the latency arm needs at least 5 successful runs in those 15 minutes |
| `PathDegradedEnterAfter` | 2 | consecutive evaluations that find the condition before the path enters degraded |
| `PathDegradedLeaveAfter` | 10 minutes | how long the condition must be absent before the path leaves |

A sample is a probe, counted as `MonitorRollup` counts them since M2a: every echo or request of a multi-packet run and one per run of a single-probe kind, so tcp and http count runs and a five-packet icmp or beacon run counts five. The floor guards the denominator of the ratio it qualifies, which is probes (`MonitorRollup.Loss` is lost over sent). A result with a reason counts as nothing, as everywhere else. With the base loss `B_loss` (lost over sent across the baseline buckets) and the base p50 `B_p50` (the 0.5 quantile of the merged baseline histogram, `MonitorRollup.Quantile`), the loss arm holds when probes are at least 30 and loss is strictly above both `loss_percent` / 100 and `loss_factor` times `B_loss`; the latency arm holds when `B_p50` exists, successful runs are at least 5, and the 15-minute p50 is strictly above both `latency_factor` times `B_p50` and `B_p50` plus `latency_margin_ms`. The condition is either arm. The loss trigger is therefore `max(loss_percent / 100, loss_factor * B_loss)` and the latency trigger `max(latency_factor * B_p50, B_p50 + latency_margin_ms)`; the server computes both (`model.DegradedLossTrigger`, `model.DegradedLatencyTrigger`) and sends them, so the console never re-derives them. The baseline follows the path: a long degradation slowly becomes its own baseline (the median flips once more than half the week's runs are slow, about three and a half days at a constant doubling), which is stated on the path sheet rather than hidden.

The baseline, the windows and the state are keyed by the pair the path uses now, (monitor, source), as rows and rollups are. A generated path's series joins its tcp, icmp and beacon checks for drawing, but its state is judged on the current check only (`PathCell.MonitorID`), because loss means a different thing per method; a method switch therefore starts a new 24-hour gate on the new check. A choice made here.

**Thresholds.** `model.MonitorDegradedRule`, on `Monitor.Degraded` for an operator check and on `LatencyProbeConfig.Degraded` for the path set, whose generated checks read it from the path set (they carry none of their own). Nil, an absent field and zero all read as the default. The server stores the canonical form: values rounded to one decimal place (the margin to a whole millisecond), a field equal to its default stored as zero, and the whole object as nil when every field is default, so an editor that echoes the defaults stores nothing. Validation (`model.ValidateDegradedRule`, shared by the server and its tests) refuses NaN, infinities, negatives and anything outside the bounds, naming the field.

| Field | JSON | Default | Bounds |
|---|---|---|---|
| LossPercent | `loss_percent` | 2 | 0.5 to 50, percent |
| LossFactor | `loss_factor` | 2 | 1.2 to 10, times the 7-day loss |
| LatencyFactor | `latency_factor` | 2 | 1.2 to 10, times the 7-day p50 |
| LatencyMarginMs | `latency_margin_ms` | 30 | 5 to 1000, milliseconds above the 7-day p50 |

`MonitorUpdate.Degraded` follows the edit rule of D1: absent keeps the stored rule, an object replaces it whole (so `{}` resets it to the defaults). The path set is saved whole, as today. `normalizeLatencyProbeConfig` (`latency_probes.go`) builds its output field by field, so it must copy `alert`, `alert_after` and `degraded`, or a save drops them silently; a test pins that. The windows, floors, enter count, leave time and baseline gate are constants, not settings.

**Alert policy.** `Monitor.Alert` gains `model.MonitorAlertDownAndDegraded` (`down_and_degraded`): it pages `monitor.down` exactly as `down` does and adds `path.degraded` and `path.recovered`. `validMonitorAlert` and the create path in `handleMonitors` (`server.go`) accept it on every kind but tls. The path set gains `LatencyProbeConfig.Alert` (`off`, `down` or `down_and_degraded`) and `LatencyProbeConfig.AlertAfter` (1 to 20, zero reads as 2). One resolver decides what a check does, `model.EffectiveMonitorAlert(alert string, generated bool)`: empty reads as `down` on an operator check, as it always has, and as `off` on the path set and its generated checks, so a stored path set, and every path set nobody touches, never pages, which is today's behaviour and D6's default. On the server, `monitorPolicy(mon)` returns the alert, the hold and the rule: an operator check's own fields, or for a check whose `ManagedBy` is `latency` the path set's. `monitorPages` (`monitor_update.go`) reads that resolver instead of testing `ManagedBy`, so a path set set to `down` or `down_and_degraded` pages `monitor.down` and `monitor.recovered` for its generated paths after `alert_after` failures (the incident sweep groups what falls due together into one message per type), and one left at `off` keeps the M1 skip in `notifyMonitorTransition`, `pendingIncidents` and the startup adoption in `incidents.go`. `pathStateOf` reads the same hold for a generated path's down. The beacon reachability checks (`ManagedBy` `beacon`) are not paths and never page.

**The evaluator.** `startPathDegradedEvaluator` runs beside the latency probe sync and the history prune (it joins `latencySyncLoops` and stops on `latencySyncStop`); the first evaluation runs one minute after start and then every minute. One evaluation:

1. Lists the paths (`pathEntries`, all of them, before any caller's scope) and keeps those that can have results: a check exists, the kind is not tls, the check is enabled, the source is assigned and not paused, the source runs the kind (no gate) and the target resolves. A record held for a pair that is no longer on that list is dropped (below).
2. Reads the windows in one call, `store.MonitorRowSummaries(pairs, now - 1h, now - 15m, now + 1ns)`: `Cur` is the last 15 minutes, `Prev` the 45 before, and `Cur` merged with `Prev` is the last hour. That is the raw tier, the one the 1 h matrix window already reads, and it covers the hour at any interval because a path keeps 1440 rows and the interval floor is 10 s. Raw rows give the windows exact edges; five-minute rollups would be cheaper (measured below) but would make "the last 15 minutes" anything from 10 to 15. A choice made here.
3. Refreshes the baselines when the hour has turned since the last refresh, in one read over every listed pair at the coarse tier, and reads a pair it has no baseline for alone. The read is a new `store.MonitorRollupBaselines(pairs, from, to)` beside `MonitorRollupSummaries` (`store/monitor_history.go`): one bolt read transaction outside the store lock, one seek per pair, a reused scratch record, returning per pair the merged bucket and the count of buckets with at least one countable run. Baselines stay in memory only; a restart reads them again at its first evaluation.
4. Judges the condition per pair with the pair's rule and steps its record as the table below says.
5. Publishes a new snapshot of every record by swapping one map under a mutex, as the matrix cache does, so a matrix read never waits for the evaluator's store reads and the evaluator never waits for a matrix read; and stamps `degraded_at`.

| Record | Condition found | Condition absent |
|---|---|---|
| none | pending, in memory, `since` = now | none |
| pending | degraded: written with `since`, `entered_at` = now and the evidence | none |
| degraded | degraded; evidence refreshed in memory | clearing: `clear_since` = now, written |
| clearing | degraded: `clear_since` cleared, written | none once now minus `clear_since` is 10 minutes or more: record deleted |

"Consecutive" counts evaluations, not minutes, so a late tick does not reset a pending record; a restart does, because pending is not written. The record also carries `quiet`, set when it enters (pending to degraded) while the path reads down or unknown before degradation is considered (see Notifications).

The matrix reads the snapshot. `pathStateOf` keeps its order (not probeable, gated, paused, no check, agent offline, stale, unknown reason, filtered, down) and only then, where it would return up, returns `degraded` when the pair's record is degraded or clearing. Down and unknown always win, because they say more about now; the record keeps running underneath, so a path that comes back from an outage while the hour still holds its failures reads degraded until they age out. Degraded is a state for now, like up and down: it does not change with the page's window.

**Restart.** Records live in a new hot-store bucket, `monitor_path_degraded`, keyed by the pair key the latest records use (`monitorPairKey`, monitor id, slash, node id), with the value `store.PathDegradedRecord` as JSON: `since`, `entered_at`, `clear_since`, `quiet`, `reason`, and the evidence at entry. Only transitions write (enter, start clearing, stop clearing, leave), so an episode costs three small writes plus two for each time clearing is cancelled, never one a minute, and the state file is never touched. `deleteMonitorResultsTx` and `DeleteMonitorResultsForNode` (`store/bolt_monitor_results.go`) delete the bucket's keys with the rest of a pair's history. At start the evaluator loads the bucket and publishes it as its first snapshot, before its first run, so the matrix shows a degraded path with its original `since` from the first read, a clearing path keeps counting its ten minutes from the stored `clear_since`, and a pending path needs two fresh evaluations. Nothing re-alerts: the `path.degraded` incident is itself durable in the hot store, `openIncident` on a key that is already open changes nothing, and a loaded record follows the same open rule as a new one. Without the hot store (the JSON fallback, which is not production) records live in memory only, as incidents do there (`Durable` false).

**Cost at 600 paths.** Measured on 2026-10-16 with the M1 benchmark fleet (`newBenchFleet` in `monitor_paths_bench_test.go`: 25 nodes, 600 tcp paths at 60 s, an hour of raw rows, a day of five-minute and two weeks of hourly results) on an Apple M3 with 8 cores that other agents held at a load average of 33 to 42, so these are upper bounds. The minute's raw read (36,000 rows) took 50 to 87 ms; the same windows from five-minute rollups took 29 ms. The hourly baseline read (100,800 one-hour buckets) took 179 ms and 26 MB allocated as a summary read with a reused scratch record, against 611 ms and 96 MB through `MonitorRollups`, which returns every bucket; hence the new store read. Ingest p99 during the minute read was 19.7 ms, against 17.1 ms with ingest alone in the same run. At 60 s intervals the evaluator therefore spends under 0.1 core-seconds a minute on the windows and about 0.2 core-seconds an hour on the baselines; at the 10 s interval floor the hour holds six times the rows (at most 360 per path, bounded by the 1440-row cap), about 0.5 core-seconds a minute. Memory is one baseline (about 64 bytes) per path and one record per path that is pending, degraded or clearing.

**Matrix fields** (`GET /api/monitors/paths`, `model.PathMatrix` and `model.PathCell`):

| Field | JSON | Meaning |
|---|---|---|
| PathMatrix.DegradedAt | `degraded_at` | when the evaluator last ran; null before its first run after a start. Always present on an M3 server, so the console tells a server that judges degraded from one that does not by the key, and a state the server does not compute is never shown |
| PathCell.State | `state` | gains `degraded` (`model.PathStateDegraded`) |
| PathCell.Reason | `reason` | for a degraded path, `degraded_loss`, `degraded_latency` or `degraded_loss_latency`, by the arms that held at the last evaluation that found the condition; prefixed so one reason table serves both states, as D12 prefixed the beacon's. Unknown keeps its reasons |
| PathCell.Degraded | `degraded` | `model.PathDegradation`, present only while the state is degraded |

`PathDegradation` is `since` (the first of the two evaluations that entered), `evaluated_at` (the last evaluation that found the condition, which the evidence is from), `clearing_since` (absent while the condition holds; the path leaves ten minutes after it), `loss` and `latency`. `loss` (`model.PathLossEvidence`, present when the loss arm held) is `value`, `baseline` and `trigger` (shares, 0 to 1) with `sent` and `lost` (probes in the hour); `latency` (`model.PathLatencyEvidence`, present when the latency arm held) is `p50_ms`, `runs` (successful runs in the 15 minutes), `baseline_ms` and `trigger_ms`. Figures are rounded as the rest of the matrix rounds them. The matrix keeps its scope rule; a path a caller cannot read is not in the matrix, and neither is its record.

**Series fields** (`GET /api/monitors/series`, `model.PathSeries`):

- `baseline` (`model.PathBaseline`), always present on an M3 server and null for a tls check or a generated path with no current check: `from` and `to` (the baseline window), `hours` (buckets with runs in it), `ready` (hours at least 24), `p50_ms` and `loss` (null without data), `trigger_p50_ms` and `trigger_loss` (null until ready, and the latency trigger also while `p50_ms` is null), and `rule`, the thresholds in force with defaults filled in. For a series by (source, target node) it is the baseline of the pair the path uses now, the one its state is judged on; for a series by (monitor, source) it is that pair's. It reads the evaluator's cache, and reads the pair's baseline once when the cache lacks it (a paused path, which the evaluator does not judge).
- `previous` (`model.PathPreviousSeries`), present only when the request adds `compare=previous` (any other value of `compare` is a 400): `from` and `to` (the window one span earlier), `offset_seconds` (the span), `step_seconds` (the resolution it was read at) and `p50_ms`, one entry per entry of `buckets`, null where the earlier step had no successful run. Entry i covers [t_i minus the span, t_i minus the span plus the step), read from the same checks for the same source at the finest tier that holds the whole earlier window; when that tier is coarser than the series' step (a 7 d window's previous week falls outside a 7-day fine retention), one coarse bucket gives its value to every step it covers. It doubles the series read and is made only when asked. Scope and errors are the series route's.

**Freshness and triangulation.** Triangulation is a console model over the matrix (`src/views/fleet/triangulationModel.ts`); the server adds nothing for it. Freshness is per path and the server already decides it: a path whose state is `up`, `degraded` or `down` has a newest outcome no older than `max(3 intervals, 2 minutes)` at `observed_at` (`pathStaleAfterRuns`, `pathStaleFloor`) from a source whose agent is online, because `pathStateOf` reads every other path unknown. So a fresh path is one whose state is up, degraded or down, and the console never re-judges freshness with its own clock. A choice made here: no freshness field is added, since any field would restate what the state already says.

The model runs two families over every row of the matrix (node targets and operator check rows alike): reach, where a path is bad when down and good when up or degraded, and quality, where a path is bad when down or degraded and good when up. For a bad path from source S to row T, in this order:

1. **The target**: T has fresh paths from at least two sources and every one of them is bad. Evidence: "Down from all 3 sources that report on it: cd-hs-sh, hk-edge, fra-1" (quality: "Down or degraded from all 3 ...").
2. **This source's network**: S has bad paths to at least three rows and to more than half of the rows it has fresh paths to, and at least one of those rows has a good fresh path from another source. Evidence: "cd-hs-sh fails 7 of the 9 targets it reports on; other sources reach 5 of them."
3. **This path**: anything else. Evidence: "2 other sources reach tyo-3" when other fresh sources exist, else "Only cd-hs-sh reports on tyo-3, so the cause cannot be placed."

The corroboration in rule 2 is what keeps D6's sentence true: with one source, rules 1 and 2 can never hold and every verdict is "this path". A verdict is a label with its evidence in the Overview attention list and on the path sheet. It changes no state, opens no incident and sends nothing.

## Risks

- **Beacon surface.** Mitigated by D3: no reply to anything unsigned, exact-length requests, no amplification, keys held by the server, rate limits after authentication, panic recovery and a circuit breaker, the per-node plan, NetGuard companion rules with `notrack`, and the node veto. A security review of the responder is part of M2b's acceptance.
- **Storage growth** with large meshes; mitigated by the fixed raw and coarse tiers, the 14-day ceiling, the pruning sweep, measured size on the settings page and the 300-path warning. bbolt does not shrink its file; that is stated, not hidden.
- **Read contention.** The 7-day matrix is the expensive read, not ingest; it reads coarse buckets, is cached per window and runs outside the store mutex. The M1 benchmark checks it under ingest.
- **Doctrine drift.** The amendment is narrow and written down; any second inbound socket on the agent needs its own design.
- **Older agents.** Capability gating keeps an agent that predates M2a on tcp, reading unknown for methods it cannot run instead of down.
