# 攻击检测、告警与通知:设计

状态:设计稿,未实现。前置条件 SSH Guard 已发布,检测与告警本身还没做。

起因是一次实测:扫全舰队 24 台可达节点,`qqpw_hawaii_vds` 一天被打 8449 次密码爆破且**密码登录还开着**,`openjobs_vpn_gomami_jpn` 2224 次,`dmit_eb_wee_us` 2123 次,好几台在 800 到 1200 之间。而 HK 装上门之后,近一小时 sshd 的爆破失败记录是 **0**。

## 已有的地基,以及缺的那一块

`lattice-node-agent/internal/sshwatch` 已经在解析 sshd 日志,但**只认成功登录**(`Accepted ...`),不跟踪失败。它的解析器有个想得很清楚的安全性质值得保留:必须整条消息匹配,因为用户名由未认证的远端选择而 sshd 会原样回显,任何允许"消息中间出现"的模式都能被攻击者打进去。

服务端这边:agent POST `{node_id, kind, ...}` 到安全事件接口,按 `kind` 分派,`ssh_login` 记审计(`Decision: observe`)再发通知。通知规则(`model.NotifyRule`)按事件类型订阅,渠道有 telegram、bark、discord、webhook。**当前全系统只有两个事件类型:`monitor.down` 和 `ssh.login`。**

所以框架是全的,缺的是攻击类事件本身。

**一个要顺手修的弱点**:`classifyNotifyEvent`(`internal/server/server.go:4414`)是按通知**标题的文本子串**推断事件类型的。改一句措辞就会静默改变谁收到通知。新事件应当把类型显式带上,而不是从散文里猜。

## 检测放在哪:agent 侧聚合,不是日志上送

单台一天 8449 行失败,30 台就是每天 25 万行。把它们送到服务端再分析,既贵又没意义 —— 没人会去看。agent 本来就在 tail 那份日志,让它就地聚合成一份紧凑摘要:窗口、失败总数、不同来源数、前几名来源、以及**失败之后是否有成功**。

## 什么值得告警,什么只该记录

这是整个设计里唯一难的判断。**对"你正在被爆破"告警是错的** —— 每台公网机器都在被爆破,这种告警会天天响,然后被静音,然后真出事时没人看。经典的失败模式。

告警只留给需要人**现在**动手的事:

- **同一来源失败多次之后成功登录**。这是可能已被攻破,最高优先级。
- **从未见过的来源成功登录**。值得知道。
- **策略说只用密钥的节点上出现密码登录成功**。策略漂移,而且说明加固没生效。
- **root 直接登录成功而策略禁止它**。
- **速率相对基线突增一个数量级**。区分"背景噪音"和"有人盯上你了"。

其余的属于**姿态报告**,是需要某天做决定的事,不是需要现在动手的事,所以进报表不进通知:公网节点还开着密码登录、`LoginGraceTime` 还是默认 120、没有防火墙门、`MaxAuthTries` 还是 6。

这条区分是整个功能的价值所在,否则它就只是个 `grep` 加推送。

## 新增的事件类型

- `ssh.compromise_suspected` —— 失败后成功,带来源、用户、方法、之前的失败次数。
- `ssh.login_new_source` —— 成功登录来自此前未见的来源。
- `ssh.policy_drift` —— 实际生效的 sshd 配置与该节点的 SSH Guard profile 不符。
- `ssh.pressure_spike` —— 失败速率相对该节点基线突增。

姿态类走 `GET /api/security/ssh-posture`,不发通知。

## 姿态数据从哪来

`guardreality` 采集器现在只跑 `ss -tulpnH`、`ip addr`、`nft -j list ruleset`、`nft --version`,读不到 sshd 配置,也不知道 knockd 装没装。要做姿态报告和漂移检测,得扩这个采集器:加一次 `sshd -T` 的解析结果(只取白名单字段,不上送整份配置),以及 knockd 的存在与运行状态。

这是 agent 侧改动,需要一次 agent 发布,所以排在 SSH Guard 之后。

## 交付顺序

1. agent:`sshwatch` 增加失败行解析与窗口聚合;`guardreality` 增加 sshd 姿态字段。
2. 服务端:新增四个事件类型与判定;`classifyNotifyEvent` 改为显式类型;姿态接口。
3. 控制台:姿态总表(哪些节点弱在哪),以及告警的处置入口。
4. 通知:双 Bark 交叉验证(见 `_archive/2026-08/TASK-QUEUE.md` Q19),让"HK 自己挂了"这种情况也有人被叫醒。

## 一条必须写死的约束

**攻击检测的告警不能依赖被攻击的那台机器把消息发出去。** 判定发生在服务端,通知也由服务端发,agent 只上报观测。否则一台被打瘫或被攻破的机器,恰恰是最不可能替你报警的那一台。
